# n8nワークフローJSON ルール

## 情報源の優先順位

1. 接続先n8nインスタンスから取得できる実際の情報（エクスポート済みJSON・API応答）
2. n8n公式ドキュメント（docs.n8n.io）
3. n8n公式GitHubリポジトリ（n8n-io/n8n）
4. Anthropic公式Claude Codeドキュメント
5. 使用する外部サービスの公式APIドキュメント
6. 使用する公式SDK／公式パッケージ

非公式ブログ・SNS・動画・掲示板は補助情報としてのみ使用し、仕様の確定根拠にしない。

## 推測で生成してはいけないもの

- ノードの正式名称・`type`・`typeVersion`
- ノードパラメータの正確なキー名・値
- Credential Type
- 架空のWorkflow ID / Webhook ID / Credential ID
- APIのエンドポイント・認証方式・リクエスト/レスポンス形式・必須フィールド
- 動作確認結果・実行結果・デプロイ結果

確認できない項目は `[未確認]` `[要公式確認]` `[要インスタンス確認]` `[ユーザー入力待ち]`
`[実行環境なしのため未テスト]` を明記する。架空の値を入れて埋めない。

## 生成時の方針

- 可能であれば、接続先n8nインスタンスからエクスポートした最小構成のワークフローを参照し、
  その形式（フィールド名・ネスト構造）に合わせる。
- 未確認の `typeVersion` やパラメータは、ドラフト内で明示的に `[要インスタンス確認]` と
  コメントし、`n8n-schema-researcher` の確認が完了してから `workflows/validated/` へ進める。
- 分かりやすいノード名、ノードの役割が分かる注記（`notes` 相当）、論理的な配置、
  エラー経路・例外処理・データ検証・監視ポイントを可能な範囲で含める。

## 設計時の必須技術観点

冪等性、二重実行防止、入力値検証（null・空配列・欠損値）、データ型の統一、
タイムゾーンの明示、日付形式の統一、ページネーション、バッチ処理、レート制限、
タイムアウト、リトライ条件（安全に再試行できるケースに限定：タイムアウト・レート制限・
一時的な通信障害のみ）、指数バックオフ、リトライ不可能なエラーの分類、部分失敗時の処理、
補償処理、エラーワークフロー、通知、ログ、監視、処理コスト、実行データの保存方針、
個人情報のマスキング、認証情報の分離、テスト環境と本番環境の分離。

作成系API（POST等）を再試行する場合は、重複登録防止の仕組み（冪等キー等）を設計する。

## ノード選定の優先順位

1. n8n公式ノード
2. HTTP Request等を利用した公式API接続
3. 検証済みのコミュニティノード
4. Codeノード（標準ノード・式だけで安全かつ明確に実装できない場合に限定）
5. 外部の独自サービス

公式ノードがあっても機能不足・バージョン差異・ページネーション非対応がある場合はHTTP API方式と比較する。
巨大な単一ワークフローにまとめず、責務ごとにサブワークフロー化する（ただし過剰分割で保守性を落とさない）。

## Credential

Credentialの秘密値・架空のCredential IDを生成しない。必要なCredentialは
マッピング表（用途→実在するCredential名）として `docs/` に整理し、実際の割り当ては
ユーザー承認のもとで行う。
