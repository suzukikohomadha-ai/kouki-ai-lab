- ワークフロー名：note運用マニュアル（社内版・自動更新・下書き分離方式）
- 一意の管理ID：AUTO-CNT-001

- 技術責任者：エイト

## 【v2で解消】情報源＝保存先の自己汚染リスク（旧・未解決の設計論点）

v1では`sourcePageOrDbId`と`destinationPageId`が完全に同一のNotionページ（「コホマダ note運用計画書v1.11」、page id: `3b0040888e978112ae4be271c3ff0a10`）に設定されており、独立監査（`logs/common_2026-08-09_n8n実装_監査_v1.md`4節）で重大な問題として非承認とされた。v2では以下のとおり分離した。

- **情報源（読み取り専用・確定）**：`sourcePageOrDbId` = `3b0040888e978112ae4be271c3ff0a10`（「コホマダ note運用計画書v1.11」）。ワークフロー内でこの値をURLに含むノードは`Notion取得：note運用計画書（情報源・読み取り専用）`（GETのみ）の1つだけ。
- **下書き保存先（書き込み対象・新規）**：`destinationDraftPageId` = `3b7040888e9781d5aebfe8ff1f46b515`（「note運用マニュアル（社内版）_自動生成下書き」、📚ナレッジDB内、事業＝コホマダ、種別＝note運用計画書。2026-08-10、ジンが社長の指示を受けて作成）。AUTO-CNT-001専用の新規ページで、本体の「note運用計画書」シリーズとは物理的に別ページ。
- **同一ID禁止ガード**：`設定値の検証`ノードに、`sourcePageOrDbId === destinationDraftPageId`ならthrowする恒久的な安全策を追加した（監査の推奨対応4節に対応）。

### 出力先ページの実装方式：2案比較

| 観点 | 案A：実行のたびに新規ページを作成（`POST /v1/pages`） | 案B（採用）：固定の下書き専用ページに毎回追記 |
|---|---|---|
| 実装の複雑さ | 高（親ID`[要確認/社長]`が別途必要、前回下書きの特定にDB検索ロジックが必要） | 低（v1の追記ロジックをそのまま流用可） |
| 必要な権限 | ページ新規作成権限が追加で必要（最小権限の原則から外れる） | GET/PATCHのみで完結、新規作成権限は不要 |
| レビュー導線 | ページが増え続け、放置・見落としのリスク | 1箇所に固定され、他のコンテンツ生成ルーティン（note/X/Instagram等）と同じ運用パターンに合致 |
| 履歴の残し方 | 実行のたびにページ単位で自動的に残る | Notionのページ編集履歴機能に依存 |
| 導入の手間 | 親DB/親ページの設計が別途必要 | 初回のみ人間が空ページを1回作成 |

**推奨：案B。** 月次・社内利用という低頻度・低リスクな性質、既存のコンテンツ生成ルーティンとの運用一貫性、最小権限の原則を踏まえ、案Bを採用してドラフトv2を実装した。案Aへの変更が必要になった場合は`n8n-optimize`フェーズで再検討する。

### 自己汚染チェック（再設計後の再確認、2026-08-09実施）

1. `sourcePageOrDbId`をURLに含むノードは`Notion取得：note運用計画書（情報源・読み取り専用）`（GET）の1つのみ。他のいかなるノードもこの値を参照しない。
2. `destinationDraftPageId`をURLに含むノードは`Notion取得：下書きページ（前回のAI生成下書き・diff/継続性用）`（GET）と`Notion - 下書きページへ書き込み（本体ページには一切書き込まない）`（PATCH）の2つのみ。いずれも下書き専用ページのみを対象とする。
3. `設定値の検証`ノードで、プレースホルダー未設定チェックに加え同一ID禁止ガードを実装（前述）。
4. Claudeへのプロンプトは、本体ページ由来のテキストを「情報源（事実の一次情報）」、下書きページ由来のテキストを「前回のAI下書き（文体・構成の継続性のみに使用、新たな事実の根拠にはしない）」として明確に分離。本体ページの内容がAI下書きの再投入によって変質することは、データフロー上あり得ない。
5. **結論：本体ページ（note運用計画書v1.11）はこのワークフローのいかなる実行によっても書き込まれることがなく、読み取り専用の参照元として物理的に分離された。次回実行時に自分自身の過去出力が「情報源」として再投入される経路は存在しない。**

### 残った未解決事項（v2でも未解決）

- 「note運用計画書」シリーズは版ごとに新規ページを作成する運用（v1.0〜v1.11）のため、`sourcePageOrDbId`を固定値のままにすると将来v1.12以降が作成された際に情報源が古いままになる可能性がある。動的に最新版を検索する設計（`16fa0285-535e-42c3-8836-b8fda84b7522`データベースを種別・事業でクエリし、更新日が最も新しいページを情報源とする等）への変更は、今回のスコープ外として`[要追加検討]`とする。ただしこれは「情報源が古くなる」リスクであり、v1で指摘された「一次資料が汚染される」リスクとは性質が異なる（データ破損ではない）。
- 下書き専用ページのpage IDは2026-08-10に確定した（`3b7040888e9781d5aebfe8ff1f46b515`、ジンが社長の指示を受けて作成）。上記「note運用計画書」シリーズの新版追従の論点は引き続き`[要追加検討]`のまま。

## 案の比較（更新方式・最低2案）

下書き専用ページに対する更新方式（追記 vs 全置換）についての比較。v2で「出力先ページの実装方式（固定ページ vs 都度新規作成）」の比較は上記「出力先ページの実装方式：2案比較」に分離したため、以下は下書きページ自体への書き込み方式のみを扱う。v2でも案Aのまま変更していない（下書き専用ページになったことで削除リスクの重大性は下がったが、Notion公式ドキュメントで未確認のDELETEエンドポイントを新たに使う設計変更は今回のスコープ外とした）。

| 観点 | 案A（採用・追記方式＋差分スキップ） | 案B（全置換方式） |
|---|---|---|
| 開発工数 | 低〜中 | 高（既存ブロックの列挙・削除・再作成が必要） |
| 月額費用 | 変わらず | 変わらず |
| 保守性 | 高（実装がシンプル） | 中（削除漏れ・削除しすぎのリスク管理が必要） |
| 拡張性 | 中（ページが徐々に長くなる制約あり。ただし下書き専用ページのため鈴木さんが随時クリア可能） | 高（常に最新の1バージョンのみ） |
| 安定性 | 高（削除操作が無いため、誤って内容を消すリスクが低い） | 中（削除APIの多重呼び出しに失敗した場合、中途半端な状態になり得る） |
| セキュリティ | 同等 | 同等 |
| ベンダーロックイン | Notion依存（両案共通） | 同左 |
| 障害時の影響 | 低（追記が失敗しても既存内容は残る。かつv2では対象が下書き専用ページのため、万一の障害があっても本体ページには影響しない） | 中（削除後の再作成に失敗すると内容が消えたままになるリスク。ただしv2では対象が下書き専用ページのため実害は限定的） |
| 必要スキル | 低 | 中（Notion Block APIの削除・作成順序制御） |

**推奨案とその理由：** 案A（追記方式）。Notion APIには子ブロックの一括置換エンドポイントが無く、全置換を安全に実装するには「既存ブロックを1件ずつDELETE」→「新規ブロックをPATCH追記」という複数ステップが必要で、`n8n-workflow-json.md`が要求する「未確認のAPIエンドポイントを推測しない」原則との整合上、DELETEエンドポイントの仕様確認（`n8n-schema-researcher`／公式ドキュメント確認）を経ていない現時点では採用しない。v2で書き込み対象が下書き専用ページに変わったことで、案Aのトレードオフ（ページが徐々に長くなる）の実害は「社内の一次資料が読みにくくなる」から「使い捨ての下書きページが読みにくくなる」に軽減された。読みにくくなった場合は鈴木さんが手動でページ内容をクリアしてよい。全置換方式への変更は`n8n-optimize`フェーズでの検討候補として引き続き明記する。
