| 観点 | 案1（改善提案v2推奨・**2026-09-27社長確定**）新規「📌Slack決定事項・DB」を新設 | 案2 📚ナレッジDB内の別ビューとして統合 |

## 技術観点チェック

AUTO-SLK-001の技術観点チェック（`workflow-design.md`参照）と大部分が共通する。決定事項固有の差分のみ以下に記す。

- [x] 冪等性：案件キー相当を`slack:<channel_id>:<message_ts>`（改善提案v2 3.2.5、AUTO-SLK-001の`thread_ts`ではなく`message_ts`である点に注意）とする。決定事項は1メッセージ＝1決定を基本とする`[仮定]`（スレッド化された決定議論をどう1件に集約するかは`[要確認]`）。
- [ ] 更新（Upsert）の要否：決定事項は「後から書き換える」概念が薄いため、AUTO-SLK-001のような「0件→新規、1件→更新」のUpsertではなく、**同一`案件キー`が既に存在する場合は新規作成をスキップしログのみ**、という簡易ロジックにするか`[要確認]`。本書では暫定的にAUTO-SLK-001と同じUpsertロジックを流用する設計とした（実装時に見直しの余地あり）。
- [x] 関連案件（relation）の自動設定：本書では**自動設定しない**（人が後から手動でリレーションを張る運用）。会話中に案件キーへの言及や📋との二重タグ付けがあれば自動リンクできる可能性があるが、判定ロジックが未設計のため`[要確認]`のまま次フェーズ以降の検討課題とする。
- [x] 決定日の設定方法：**`[要確認][仮定]`**。`slk-extract v1.0`スキーマには「決定日」に相当するフィールドが無い（`deadline`は将来の期限であり決定日ではない）。本書では暫定的に「スレッド内の最初のメッセージのts→JST日付」を決定日として使う設計としたが、複数日にまたがる議論の末に決定した場合に不正確になりうる。代替案（実行日をそのまま使う／専用フィールドをスキーマに追加する）は次節「未確認事項」参照。

## ノード構成（概念設計、`[実行環境なしのため未テスト]`）

| Notion書き込み先 | 📋Slack案件管理・DB | 📌Slack決定事項・DB（2026-09-27社長確定） |
| Notionプロパティマッピング | `AUTO-SLK-001/notion-database.md`参照 | 下記「Notionプロパティマッピング」参照 |

## Notionプロパティマッピング（`slk-extract v1.0`→📌決定事項DB、確定設計）

| Notionプロパティ | 型 | マッピング元 | 備考 |
|---|---|---|---|
| 決定事項 | title | `title` | そのまま |
| 決定日 | date | `[仮定]` スレッド内最初のメッセージのts→JST日付 | `slk-extract v1.0`に決定日専用フィールドが無いための代替。`[要確認]` |
| 決定内容 | rich_text（AI要約） | `summary` | そのまま |
| 根拠Slackリンク | url | `chat.getPermalink`（対象メッセージ） | AUTO-SLK-001の「元Slackリンク」と同じ取得方法 |
| 関連案件 | relation（→📋案件DB） | 自動設定なし | 人が手動でリレーションを張る運用（上記「技術観点チェック」参照） |
| 事業 | select | 固定値`コホマダ` | |
| 要確認 | checkbox | `overall_confidence`＜0.7`[仮定]` または `ambiguities`非空 または `injection_suspected` | AUTO-SLK-001の3.3.4フォールバック表と同じロジックを流用 |
| 案件キー | rich_text | `slack:<channel_id>:<message_ts>` | 重複判定キー |
| 最終処理イベントID | rich_text | Slack `event_id` | 再送重複の排除 |

`next_actions`（Claude出力に含まれる）は、決定事項DBの専用プロパティが無いため、**ページ本文に箇条書きとして記録するのみ**とする（自動での案件DBへの起票・割当候補化は行わない）。会話の中に📋も同時に付けられている「二重タグ」ケースの扱いは`[要確認]`（AUTO-SLK-001とAUTO-SLK-002のどちらが優先処理するか、両方処理して重複記録にならないか、の設計が必要）。
