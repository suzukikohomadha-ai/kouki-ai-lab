## トリガーとAPI呼び出し設計

- **トリガー**：Schedule Trigger（cron式）。実行曜日・時刻は`[要確認/社長]`（推奨：毎週月曜 06:00 JST、閑散時間帯）。
- **`/templates/search`のページング**：リサの調査で`?rows=N&page=N`等のページング想定は確認できたが、正確なパラメータ名（`page`か`offset`か）・`rows`の上限値・ソート順（新着順で取得できるか）は`[要公式確認]`。実装前に追加検証が必要（「設計を止める情報」参照）。
  - **重要な分岐点**：「新着順（`created_at`降順等）でソート取得できる」ことが確認できれば、毎週の差分取得は「先頭ページから、前回実行時の最新既知テンプレートIDに到達するまで」で打ち切ることができ、API呼び出し回数を大幅に削減できる。確認できない場合は、毎週も全件（約115ページ、`rows=100`想定時）を走査し、取得済みIDと突合して新規・更新を判定する必要がある。後者は`api.n8n.io`への負荷・グレーゾーンとしてのリスクをより高める設計になるため、実装前の検証結果次第で設計を再確認する。
  - **アクセス間隔**：ページ取得ごとにWaitノードで3〜5秒程度の待機を挟む（リサ調査「レート制限の明記なし→低頻度・間隔を空けたアクセス必須」の指摘に対応）。
  - **リトライ**：タイムアウト・5xx・レート制限相当のレスポンスのみリトライ対象とし、最大3回・指数バックオフ的な待機時間増加を設定する。
- **`/templates/categories`の呼び出し**：カテゴリ一覧は変化頻度が低いと想定されるため、毎週の実行冒頭で1回だけ取得する。
- **カテゴリの紐付け**：`/templates/search`のレスポンス単体でテンプレートとカテゴリの対応関係を確定できるかは`[未確認]`（「設計を止める情報」参照）。確認できない場合、カテゴリ列は空欄または`[未確認]`のまま出力する設計とし、無理に推測で埋めない。

## 初回フルバックフィル／差分更新の設計

- **初回フルバックフィル**：`/templates/search`を全ページ走査し、取得した全テンプレートIDをスプレッドシートに未登録のものとして扱い、AI要約を実行して書き込む。件数が多い（最大約11,430件、2026-08-12時点）ため、ページ間隔・要約の直列実行を考慮すると数十分〜数時間規模の実行時間になる見込み`[仮定]`。n8nの実行タイムアウト設定（`[要インスタンス確認]`）によっては、複数回の実行に分割する設計（例：カテゴリ単位・ページ範囲単位で分割実行）が必要になる可能性がある。
- **以後の差分更新**：週次実行のたびに、取得したテンプレートIDをスプレッドシートの既存ID列（またはn8n静的データのキャッシュ）と突合する。
  - スプレッドシートに存在しないID → 新規として追加＋AI要約を実行。
  - スプレッドシートに存在するID → 説明文・使用ノード等が前回取得時と変化していれば「更新」として再要約、変化がなければスキップ（AI要約コストを抑える）。
  - 変化検知は、説明文のハッシュ値（例：SHA-256）をスプレッドシートの補助列に保持し、前回ハッシュと比較する方式を提案する。
- **冪等性・重複排除**：テンプレートIDをユニークキーとして扱う。同一IDへの重複書き込みを避けるため、書き込み前に必ず既存行の有無を確認する（Google SheetsのLookupまたはn8n側でのID一覧キャッシュ）。

## AI要約ステップの設計

- **既存サブワークフローの再利用可否**：`workflows/draft/AUTO-COM-001_claude-api-subworkflow.json`を確認したところ、Execute Workflow Trigger経由で`systemPrompt`（任意）／`userPrompt`（必須）／`model`（任意、既定`claude-sonnet-5`）／`maxTokens`（任意、既定4000）／`temperature`（任意、既定1）を受け取り、Anthropic Messages APIを呼び出して`{success, text, model, stopReason, usage}`を返す実装になっている。**`model`パラメータで呼び出し元から`claude-haiku-4-5`を明示的に指定できるため、AUTO-COM-001はコード変更なしでそのまま再利用可能と判断する。**
- **モデル選定**：`claude-haiku-4-5`を第一候補とする。理由：「各テンプレの使い方まで要約」は分類・要約タスクであり、Anthropic公式指針の「Classification, summarization, extraction, Q&A → 単発のClaude API呼び出し」に該当し、複雑な推論を要さない。Opus 5は過剰性能・過剰コストと考えられるため今回は非推奨とするが、要約品質がHaikuで不十分と判明した場合の代替としてSonnet 5（費用は約3倍）、それでも不十分な場合の最終手段としてOpus 5を選択肢として残す（詳細比較は「費用対効果分析」参照）。
- **プロンプト設計方針**：
  - `systemPrompt`：「あなたはn8nワークフローテンプレートの要約担当です。渡されたテンプレート名・説明文・使用ノード一覧をもとに、社内メンバーが一読して『これは何をするテンプレートで、どう使えるか』が分かる日本語の要約を作成してください。説明文に書かれていない機能や効果を推測で付け加えないでください。」を基本方針とする（AUTO-COM-001が付与する共通ガードレール「事実と推測を明確に分ける／実在しない情報を作成しない」と重複しない範囲で、テンプレート要約タスク固有の指示を追加する）。
  - `userPrompt`：テンプレート名・`description`原文・使用ノード一覧（`nodes[].displayName`等）を構造化して渡し、「1. 何をするテンプレートか（1〜2文） 2. 主な使用ノード 3. 使い方・活用イメージ（1〜2文）」の3点セットで出力するよう指示する形式を提案する。
  - `maxTokens`：要約は短文で足りるため、AUTO-COM-001の既定4000より小さい値（例：500〜800）を明示的に指定し、出力コストを抑える。
- **1テンプレートあたりの処理**：Loop Over Items相当のノードで1件（または少数バッチ）ずつExecute Workflowノードを呼び出す。個別の要約失敗（`continueOnFail`）は当該行の要約欄を「要約失敗（後日再試行）」として記録し、全体の処理は継続する。

## エラー処理

- **既存サブワークフローの再利用可否**：`workflows/draft/AUTO-COM-002_error-handler.json`を確認したところ、Error Trigger→重複排除→LINE Broadcast通知（失敗時はNotionフォールバック）という構成の汎用エラーハンドラーであり、対象ワークフロー固有のロジックを持たない。**本ワークフローのSettings > Error WorkflowにAUTO-COM-002をそのまま割り当てることで再利用可能と判断する（コード変更不要）。**
- ただし、AUTO-COM-002自体の設計書（`docs/cases/AUTO-COM-002/workflow-design.md`）には、LINE Credentialの技術的な疎通確認が本番投入前に未実施であること、Notionフォールバック格納先の恒久採用について社長の正式承認が未了であることが明記されている。KNW-001をAUTO-COM-002に依存させる場合、これらの前提条件がKNW-001本番稼働時点で解消済みかを`n8n-deploy`フェーズで再確認する必要がある。
- ワークフロー全体の異常終了（`api.n8n.io`からの応答が想定外の形式で処理を継続できない場合等）はthrowしてAUTO-COM-002へ委譲する。個別テンプレート単位の失敗（要約失敗・Sheets書き込み失敗）はワークフロー全体を失敗させず、ログに記録した上で処理を継続する設計とする（通知の粒度を分ける）。

## 投稿者個人情報の扱い

- `api.n8n.io/templates/search`のレスポンスには、各テンプレートの投稿者情報（`user`欄：表示名・ユーザー名・自己紹介・アバターURL・認証バッジ有無）が含まれることをリサが確認済み。これはn8n Creator Hub上で投稿者本人が公開している情報であるが、社内ナレッジ用途であっても転記範囲は最小化する設計とすることを推奨する。
- **推奨する転記範囲**：投稿者の表示名のみ（テンプレートの出典・信頼性の参考情報として有用なため）。自己紹介文・アバターURL・認証バッジの有無は転記しない。
- **理由**：表示名以上の情報（自己紹介文等）は、社内ナレッジとしての実用上の必要性が低い一方、個人情報の保持範囲を不必要に広げることになるため、`.claude/rules/security-policy.md`が定める個人情報の最小化・仮名化の考え方と整合させる。
- **社長判断が必要な点**：投稿者表示名の列自体を設けるか（出典として有用）、完全に省略するか（個人情報を一切保持しない）は、本設計書では両論併記とし、最終的な採否は社長の判断を仰ぐ。

## 費用対効果分析

**前提（すべて`[仮定]`。実際のトークン数は未計測）**：

- 1テンプレートあたりの要約用入力（テンプレート名＋説明文＋使用ノード一覧＋プロンプト固定部分）を平均300トークンと仮定`[仮定]`。
- 1テンプレートあたりの要約出力（3点セットの短い要約）を平均150トークンと仮定`[仮定]`。
- 対象件数：初回バックフィル 11,430件（2026-08-12時点の`totalWorkflows`）、週次差分は新規・更新あわせて1回あたり50件と仮定`[仮定]`（n8n公式テンプレートの増加ペースは未確認のため、あくまで桁数を把握するための仮の値）。

**料金表（2026-08-12時点でAnthropic公式スキルから確認済み）**：

| モデル | 入力 $/1M | 出力 $/1M |
|---|---|---|
| Claude Haiku 4.5 | $1.00 | $5.00 |
| Claude Sonnet 5（〜2026-08-31導入価格） | $2.00 | $10.00 |
| Claude Sonnet 5（通常価格） | $3.00 | $15.00 |
| Claude Opus 5 | $5.00 | $25.00 |

**初回フルバックフィル試算（11,430件、入力300トークン×出力150トークン/件の仮定）**：

- 総入力トークン：11,430 × 300 ＝ 約343万トークン
- 総出力トークン：11,430 × 150 ＝ 約171万トークン

| モデル | 入力費用 | 出力費用 | 合計（概算） |
|---|---|---|---|
| Haiku 4.5 | 約$3.4 | 約$8.6 | **約$12** |
| Sonnet 5（導入価格） | 約$6.9 | 約$17.1 | 約$24 |
| Sonnet 5（通常価格） | 約$10.3 | 約$25.7 | 約$36 |
| Opus 5 | 約$17.2 | 約$42.8 | 約$60 |

**週次差分の試算（1回あたり新規・更新50件の仮定）**：

| モデル | 1回あたり概算 | 月あたり概算（週4回換算） |
|---|---|---|
| Haiku 4.5 | 約$0.05 | 約$0.2 |
| Sonnet 5（通常価格） | 約$0.15 | 約$0.6 |
| Opus 5 | 約$0.26 | 約$1.0 |

**分析**：
- 初回バックフィルはHaiku 4.5とOpus 5で約5倍のコスト差（$12 vs $60）が生じるが、いずれも一度きりの支出としては小額である。
- 週次差分の運用コストはどのモデルを選んでもほぼ無視できる水準（月$1未満）であり、モデル選定によるランニングコストの差は実質的な意思決定要因にならない。
- したがって、モデル選定はコストよりも要約品質・処理速度で判断してよい。Anthropic公式指針（分類・要約・抽出タスクには単発呼び出しで十分）とタスクの性質（短い定型要約）を踏まえ、**Haiku 4.5を第一候補として推奨する**が、初回バックフィルの一度きりの支出増（約$12→$24〜36の差）を許容できるなら、要約品質を優先してSonnet 5を選ぶことも合理的な選択肢である。Opus 5は今回のタスクに対しては明らかな過剰性能・過剰コストと考えられるため推奨しないが、断定はせず選択肢として残す。
- **重要な留保**：上記はすべて`[仮定]`のトークン数に基づく概算であり、実際の`description`フィールドの長さ・言語（英語/多言語混在）・プロンプト設計次第で±数倍のブレが生じ得る。初回バックフィル実行前に、少数サンプル（例：20〜50件）で実測し、試算を更新することを推奨する。

## 部署略称の新設について

`docs/architecture.md`の既存部署略称（`COM`＝共通基盤、`CNT`＝コンテンツ下書き生成、`PUB`＝公開テンプレート／Creator Hub提出用）はいずれも今回の性質（社内向けの外部情報収集・整理）と一致しない。

- `COM`は「特定事業・特定業務に紐づかない共通サブワークフロー」を指すが、本案件は「n8n公式テンプレートという外部情報源を収集・整理する」という具体的な業務目的を持つため不一致。
- `CNT`は「コンテンツ下書き生成」（社外公開前提のnote・SNS等の文章生成）を指すが、本案件は社外公開しないナレッジ整理であり性質が異なる。
- `PUB`は「n8n公認クリエイター制度への提出用テンプレート」を指すが、本案件は逆に他者のテンプレートを収集する側であり、意味が正反対になる。

**提案する略称：`KNW`（Knowledge／ナレッジ収集系）**。理由：本案件の本質は「外部情報源（n8n公式テンプレートギャラリー）を定期的に収集し、社内で参照可能なナレッジとして整理する」ことであり、将来的に同種の「外部情報源の定期収集→社内ナレッジ化」案件（他ツールのテンプレート集、業界動向のダイジェスト等）が発生した場合にも共通して使える汎用性のある区分と考える。管理IDは`KNW-001`とする。

（`docs/architecture.md`の部署略称一覧表には、本設計書の提出とあわせて`KNW`行を追記済み。）

2. **実装（`n8n-build`）**：本設計書（トリガー設計・API呼び出し設計・差分更新設計・AI要約設計・エラー処理・Sheets書き込み設計）に基づき、`workflows/draft/KNW-001_<スラッグ>.json`を作成。AUTO-COM-001をExecute Workflowノードから`model: 'claude-haiku-4-5'`指定で呼び出す形で再利用し、AUTO-COM-002をError Workflow設定として割り当てる。
3. **新規スプレッドシートの作成**：社長承認のもと、新規Googleスプレッドシートを作成し、シートIDをワークフロー内の設定ノードに反映（プレースホルダーとして実装し、インポート後に確定）。
4. **静的検証・テスト（`n8n-review`／`n8n-test`）**：`scripts/validate-workflow.mjs`によるレイアウト検証、正常系・異常系（`api.n8n.io`応答異常・レート制限・Google Sheets書き込み失敗等）のテストケース作成・実行。
5. **本番移行（`n8n-deploy`、要承認）**：Credential割当・Error Workflow割当・Schedule Trigger有効化について、事前に社長の承認を得てから実施。初回フルバックフィルの実行タイミング・想定コストも承認事項に含める。
