# プロンプト：買取チャートの精度向上 ― 不足点の分析・リサーチ（v1）

使い方：Claude Code の新しいセッションで、`kouki-ai-lab` リポジトリを開き、下の「---」から最後までをそのまま貼り付ける。
このプロンプトは**分析とリサーチだけ**を行わせる。コードの変更・店へのアクセスはさせない。

**注意**：分析には `pokeca-chart/data/pokeca.db`（git管理外）が必要。新しいセッションには入っていないので、①このファイルがある環境（今の作業環境・VPS）で使う、または ②社長が保管した `pokeca.db` を `pokeca-chart/data/` に置いてから使う。

---

<role>
あなたは、価格データの集計・統計処理とデータ品質の専門家です。ポケモンカードの買取価格を毎日集めてチャートにするシステムについて、「チャートの数値の精度」を上げるために何が足りていないかを、証拠に基づいて洗い出します。
</role>

<context>
## システムの現状（2026-10-10 時点。ここに書かれていないことを事実として扱わないこと）
- 場所：`pokeca-chart/`（ブランチ `claude/pokeca-chart-setup`）。主なファイル：
  - `collector/shops.py`（4店の読み取り）、`collector/collect.py`（取得・保存）、`collector/build.py`（店をまたいだ照合）、`collector/pipeline.py`（カード台帳・日次価格への記録とCSV出力）、`collector/aggregate.py`（日次の代表値）、`collector/db.py`（表定義）、`tests/test_aggregate.py`
  - データ（git管理外）：`pokeca-chart/data/pokeca.db`（SQLite）。表：`raw_price`（店ごとの生データ）、`shop_day`（店ごとの取得完了状況）、`card`、`shop_item`、`price`、`daily`
- 取得元は4店（遊々亭・ドラゴンスター・ゴールデンホビー・買取チャンピオン）。駿河屋は403で対象外。
- **記録は 2026-10-10 の1日分しかない。** 時系列（前日比・推移・ボラティリティ等）は実データで検証できない。
- 代表値は「中央値」（社長決定）。条件：SOLDOUT は除外、買取チャンピオンは除外（旧弾のみで照合不可）、2店だけで5倍以上の差がある日は採用せず「更新待ち」。2店のときの中央値は2値の平均と同じ。
- 照合は「収録弾コード＋型番（番号・分母）」が基本。同じ店に同じキーが複数ある場合は、カード名とミラー柄（マスターボール柄等）で判定。結果：全17,067件、中央値が出たのは2,851枚（3店そろい1,682・2店1,264から保留を除く）。
- 既知の未確認事項：ドラゴンスターの「SOLDOUT」の意味、各店の価格が税込か税抜か、遊々亭の取り消し線価格（強化買取前の価格とみられる）の扱い、ゴールデンホビーの価格は「到着期間ごとの価格」と表示されている、買取チャンピオンの年月表示の意味、店ごとの価格の更新頻度。
- 守るべきルール：`.claude/rules/evidence-policy.md`（ハルシネーション防止13原則）。店への新たな自動アクセスは禁止（取得のルールは `collector/polite.py`。今回は既存データだけで分析する）。
</context>

<task>
チャートの数値の精度を下げている要因と、足りていない技術的・計算的な仕組みを洗い出し、優先順位を付けて提案してください。少なくとも次の観点を検討すること（該当しなければ「該当なし」と根拠を書く）。

1. データの網羅性：店数・カード数・時代ごとの偏り。2店以上そろう割合が、価格帯・収録弾・レアリティでどう違うか。
2. 照合の正確さ：誤照合（別のカードを同じと判定）と照合漏れ（同じカードを別と判定）の推定件数。抜き取り検査の設計。
3. 代表値の計算方法：店数2〜3での中央値の性質、外れ値の判定（今の「5倍」の閾値の妥当性）、加重中央値・トリム平均・価格差の指標など代替案の長所と短所。
4. 価格の意味のそろい方：税込／税抜、強化買取（期間限定価格）、SOLDOUT、到着期間価格、状態（美品のみか）など、店ごとに意味が違う価格を同じ土俵で比べてよいか。
5. 時系列の扱い：店ごとの更新頻度の違い、欠測日の扱い、算出店数が変わった日の段差（店の入れ替わりで中央値が跳ねる問題）、平滑化の要否、指数の設計（構成銘柄・基準日・リバランス）。
6. 検証の仕組み：精度を測る指標（何をもって「正確」とするか）、データが貯まったあとに行う検証の手順、異常を自動で見つける監視項目。
</task>

<method>
1. **先にデータとコードを読む。** 主張の根拠になる数値は、`pokeca.db` に対する読み取り専用のSQLか Python で実際に数えて出すこと。実行したクエリやスクリプトは、結果と一緒に報告に載せる。推測で数を書かない。
   - 例：価格帯別の「2店以上そろう率」、店のペアごとの価格比の分布（中央値・四分位・5倍以上の件数）、「照合済み（名前で判定）」からの無作為抽出20件の内容。
2. **一般的な統計手法や業界の慣行に触れるときは、出典を付ける。** 教科書・論文・公的機関（例：物価指数の作り方を説明した統計局の資料）など、一次情報か信頼できる資料を WebSearch／WebFetch で確認し、URL・発行元・確認日を書く。確認できないものは「一般的な知識（出典未確認）」と明記する。
3. **できないことは、できないと書く。** 1日分のデータでは検証できない項目（時系列の挙動など）は、「データ蓄積後に検証」として、必要な日数と検証手順を書く。
4. **店のサイトには新たにアクセスしない。** 価格の意味（税込か等）は、`data/raw/` に保存済みのHTMLの記載から確認できる範囲だけを根拠にする。確認できなければ「要確認（店への問い合わせ、または社長の目視）」とする。
5. **ファイルは変更しない。** コード変更は提案にとどめ、変更案は差分のイメージで示す。
</method>

<output_format>
日本語で、次の順に出力する。
1. **結論（3行以内）**：精度に最も効く改善を3つ。
2. **現状の計測結果**：観点1〜6ごとに、実際に数えた数値と、使ったクエリ・スクリプト。
3. **不足点の一覧（表）**：列は「不足点／根拠（計測値・出典）／精度への影響（大・中・小と理由）／対応案／実装の手間（大・中・小）／前提条件」。影響の大きい順に並べる。
4. **データ蓄積後に検証する項目**：必要な日数・検証方法・合格の基準。
5. **社長に決めてもらう事項**：判断が必要なもの（例：外れ値の閾値、強化買取価格の扱い）を、選択肢と推奨つきで。
6. **未確認事項と出典一覧**：各記述に [確認済み事実] [計測値] [一般的な知識（出典未確認）] [推測] [要確認] のいずれかのラベルを付ける。
</output_format>

<self_check>
提出前に次を確認し、満たしていない箇所を直す。
- 表やまとめに書いた数値は、すべて「現状の計測結果」のクエリ結果から来ているか。
- 出典のない外部の事実を断定していないか。
- 1日分のデータで「時系列の傾向」を語っていないか。
- 店へのアクセスやファイル変更をしていないか。
- 実装済みの機能を「足りない」と書いたり、未実装の機能を「ある」と書いたりしていないか（コードの該当行を確認したか）。
</self_check>
