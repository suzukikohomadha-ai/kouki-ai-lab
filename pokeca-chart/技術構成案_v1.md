## 推奨構成（結論）

| 項目 | 推奨 | 理由 |
|---|---|---|
| 言語 | Python 3 | `fetch_test.py` が標準ライブラリのPythonで作成済み。VPS（Ubuntu 24.04）に最初から入っている |
| データ保存 | SQLite（1ファイル） | 日次で数千〜数万行の追記が中心。サーバー不要・バックアップはファイルコピーだけ |
| 定期実行 | systemd timer（または cron） | 1日1回・深夜。追加費用なし |
| サイト表示 | 毎日の収集後に「静的ファイル（HTML+JSON）」を生成して配信 | 表示側にDB・アプリを持たないので、壊れにくく、軽く、安い |
| 配信 | 同じVPSのnginx、または静的ホスティング | 追加費用を月0〜数百円に抑えられる |
| チャート描画 | 軽量なJSライブラリ（外部CDNを使わず自サイトに同梱） | デモのSVG描画ロジックを流用可能 |
| マイコレクション | 端末内保存（localStorage） | デモの想定どおり。会員登録不要 |

## 代替案

- 案C：WordPress。引き継ぎ資料の【提案】で不採用。

## 設計メモ

- 公開の優先順位：収集（価格履歴の蓄積）が先、画面は後。
- 価格履歴は上書きせず1日1行追記（資料5.1）。
- 店ごとの取得部分は「1店＝1ファイル」に分け、店が作りを変えたとき、その店だけ止められるようにする（資料3.6）。
- 生HTMLは日付つきで一定期間保存。パーサーを直したとき再解析できる。
- 取得の作法（5秒以上の間隔・Crawl-delay順守・拒否時はその日停止・User-Agentで連絡先を名乗る）はコードの共通部品に固定する。
