## 結論

社長回答「名前が『コウキAIラボ』の公式LINE」を一次情報として確定事実とした上で、AUTO-COM-002（共通エラーハンドラー）の通知経路を、LINE Messaging API（Push Message）を主経路、既存のNotion通知をフォールバック（LINE送信失敗時の代替経路）とする2段構成に変更した。ただし、このLINEアカウントのチャネルアクセストークンが実際にn8n上のどのCredentialに対応するかは技術的に未確認のまま残っており、送信先（`to`のuserId、またはbroadcast可否）も未確定のため、いずれもプレースホルダー（`[要確認/社長]`）として実装している。架空のuserId・Credential IDは一切生成していない。

静的検証は`scripts/validate-workflow.mjs`でエラー0件（警告1件：Sticky Note孤立、想定通り）、`scripts/check-secrets.mjs`で「本番らしきURL」の誤検知3件（`api.line.me`のドキュメントURL・GitHub上のLINE公式OpenAPI定義URL・`api.notion.com`）のみで、Credentialの実値・実ID・トークンの混入は無いことを確認した。

## 確認済み事実

- LINE Messaging API「Send push message」（`POST https://api.line.me/v2/bot/message/push`）の仕様は、`developers.line.biz`の該当ページがJavaScriptで動的レンダリングされておりWebFetchでは本文を取得できなかったため、LINE公式GitHubリポジトリ`line/line-openapi`（`messaging-api.yml`、2026-08-09時点のmainブランチ、`curl`による直接取得＝読み取り専用）で代替確認した。確認できた主要仕様：
  - パス：`/v2/bot/message/push`、メソッド：`POST`（`operationId: pushMessage`）
  - リクエストボディ（`PushMessageRequest`）必須項目：`to`（string、受信者ID）・`messages`（`Message`オブジェクトの配列、`minItems: 1`／`maxItems: 5`）。任意項目：`notificationDisabled`（boolean）。
  - 認証：`securitySchemes.Bearer`＝`type: http, scheme: bearer, description: "Channel access token"`（＝Authorization: Bearer <チャネルアクセストークン>）
  - テキストメッセージ（`TextMessage`）は`type: "text"`と`text`（string）を持つ。同スキーマ定義に文字数上限（`maxLength`）の記載は無く、公式ドキュメントページからも数値を確認できなかった（`[要公式確認]`のまま残す。本ドラフトは安全側に1900文字で切り詰め）。
  - 応答：200＝`PushMessageResponse`（`sentMessages`配列）、400/403/409/429＝`ErrorResponse`。
  - 代替エンドポイントとして`/v2/bot/message/broadcast`（`BroadcastRequest`、`to`不要、友だち全員に送信）の存在も確認した（本ドラフトでは未実装、送信先userIdが最終的に得られない場合の代替案としてSticky Note・設計書に明記）。
- n8n公式ドキュメント（HTTP Requestノードの認証方式一覧・Credentials参照ページ）で、Generic CredentialsのうちBearer Authが「Header認証の特殊形（`Authorization: Bearer <token>`を自動構築）」であることを確認した。ただし、HTTP RequestノードのJSONパラメータ上で`authentication: "genericCredentialType"` / `genericAuthType: "httpBearerAuth"`という具体的なキー名の組み合わせは、n8nの一般的な実装パターンとして認識しているものであり、本インスタンスでの実例（エクスポート済みJSON）では確認できていない（`[要インスタンス確認]`として明記した）。
- T105/第2弾で確認済みの`httpBearerAuth`型Credential（`id: QpSnEXPfPjtBKSVD`、`name: "Bearer Auth account"`）は、依然として名称のみでLINE用である確証は無い。**今回のセッションでも値の取得・追加照会は行っていない。**

## 現在の仮定

- `httpBearerAuth`Credential（`Bearer Auth account`）が実際に「コウキAIラボ」公式LINEのチャネルアクセストークンを保持している、という仮定を置いて設計上の第一候補としているが、確証は無い。本番投入前に必ずn8n UI上での確認が必要（下記「未確認事項」・ワークフローJSON内Sticky Note参照）。
- n8n HTTP Requestノード（typeVersion 4.2）が`genericCredentialType`＋`genericAuthType: httpBearerAuth`という組み合わせで、既存の`httpBearerAuth`型Credentialをそのまま利用できるという仮定（n8nの一般的仕様として認識しているが本インスタンス実例は未確認）。

## 分析（設計判断の要点）

### 1. 通知経路の設計変更：LINE主経路＋Notionフォールバック

`IF: 重複チェック`通過後、`設定：通知先（要確認/社長）`（Setノード、`lineTargetTo`・`destinationDatabaseId`のプレースホルダーを保持）→ `LINE通知メッセージ本文生成`（Code、`to`/`messages`を構築）→ `LINE - Push通知送信`（HTTP Request、`continueOnFail: true`）→ `LINE送信結果判定`（Code、成功/失敗を正規化）→ `IF: LINE送信失敗判定` で分岐し、成功なら終端、失敗なら従来の`Notion通知ページ本文生成（フォールバック）`→`Notion - エラー通知ページ作成（フォールバック）`へ流れる構成にした。

3案（①LINE主経路＋Notionフォールバック［採用］／②LINEとNotionを常に並行実行／③LINEのみでNotion完全削除）を比較し、①を採用した。理由は、③だとCredential・送信先が未確定な現状で通知が一切残らない空白期間が生じてしまい、②だとLINEが正常稼働するようになった後もNotionに毎回ノイズが残ってしまうため。詳細な比較表は`docs/cases/AUTO-COM-002/workflow-design.md`の「案の比較」節（2026-08-09追記分）を参照。

### 2. Credential・送信先の扱い

`httpBearerAuth`Credentialへの紐付けは、AUTO-COM-002のドラフトJSON上では実IDを一切埋め込まず、`authentication: genericCredentialType` / `genericAuthType: httpBearerAuth`の指定のみに留めている（インポート後にn8n UI上で手動割当てが必要）。送信先`to`は`[要確認/社長：送信先userIdまたはbroadcast可否]`というプレースホルダー文字列とし、架空のuserIdやCredential IDは生成していない。

## リスク・注意点

- **LINE Credential紐付けが未確認**：`Bearer Auth account`が実際に「コウキAIラボ」公式LINEのチャネルアクセストークンかどうかは、値を見ずには判別できない。誤って無関係なBearer認証サービス用のCredentialを割り当てると、送信が失敗し続ける（＝常にNotionフォールバックが発動する）か、最悪の場合意図しないサービスへ誤送信するおそれがある。
- **送信先userIdが未確定**：プレースホルダーのまま実行するとLINE API側で400エラーとなる想定だが、これはNotionフォールバックへ自動的に流れる設計（安全側の挙動）。
- **`genericCredentialType`／`genericAuthType: httpBearerAuth`というn8n側のパラメータ名の組み合わせが本インスタンスで未検証**：n8nの一般的な実装パターンとして採用したが、実際にn8nへインポートした際にパラメータ名の不一致でエラーになる可能性がある。本番投入前に`n8n-schema-researcher`視点での追加確認、または実際にn8nエディタUIでHTTP RequestノードのBearer Auth設定を1つ試作しエクスポートJSONを確認する作業が必要（Error Trigger等、既存の未確認事項と同種の制約）。
- **LINEテキストメッセージの文字数上限が未確認**：LINE公式OpenAPI定義・公式ドキュメントいずれからも数値を確認できなかったため、本ドラフトは安全側に1900文字で切り詰めている。正確な上限は別途公式確認が必要。
- **通知内容の非対称性**：LINE送信成功時は文字数制約から簡易サマリーのみ、Notionフォールバック発動時は従来通り詳細な本文が記録される。フォールバック発動時のほうが情報量が多いという非対称な設計になっている点は運用上認識しておく必要がある。
- `check-secrets.mjs`が「本番らしきURL」として`api.line.me`のドキュメントURL・LINE公式GitHubリポジトリURL・`api.notion.com`の計3件を検出したが、いずれも公開APIエンドポイント・公式ドキュメントURLであり、シークレットではない（既存の誤検知パターンと同種、目視確認済み）。

## 推奨案

1. 社長・実弁護士ではなく技術的な最終確認として、n8nエディタUI上で以下を実施することを推奨する（本ドラフトJSONのSticky Noteにも同内容を明記済み）。
   1. Credentials画面で`Bearer Auth account`（`httpBearerAuth`種別）を開き、**値は見ずに**名称を分かりやすくリネームできるか、または作成経緯を確認する。
   2. 可能であれば、本番ワークフローとは切り離した使い捨てのテスト実行で、Push Message送信を1件だけ試し、実際に「コウキAIラボ」公式LINEに届くかを確認する（事前承認必須。送信先userIdの入手も必要）。
   3. 正しいCredentialと判明した時点で、`LINE - Push通知送信`ノードにn8n UI上で手動割当てる。
2. 送信先userIdが最終的に得られない場合は、`POST https://api.line.me/v2/bot/message/broadcast`（友だち全員への一斉送信、`to`不要）への切替を次のイテレーションで検討する。
3. Credential紐付け・送信先が確定し、LINE送信の安定稼働が確認できた段階で、Notionフォールバック経路自体を残すか削除するかを改めて社長に確認する。
4. 上記が揃い次第、`n8n-review`（`scripts/validate-workflow.mjs`・`scripts/check-secrets.mjs`の再実行、`n8n-quality-auditor`視点の独立監査）に進む。

## 代替案

- Notionフォールバックを完全に削除し、LINEのみに一本化する案：Credential・送信先が確定していない現状では通知の空白期間が生じるリスクが高いため、今回は不採用（詳細は`docs/cases/AUTO-COM-002/workflow-design.md`の「案の比較」節を参照）。
- LINEとNotionを常に並行実行する案：頑健性は高いが、LINE安定稼働後もNotionへの記録が常態化しノイズになるため、今回は不採用。
