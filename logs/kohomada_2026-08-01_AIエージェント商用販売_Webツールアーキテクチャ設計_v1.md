## 結論

- アプローチ①（Streamlit/Gradio等でUIのみ提供し、コード非開示・顧客自身のAPIキー利用）は、**技術的には実現可能**と判断する。ただし「顧客のAPIキーをサーバー側でどう扱うか」の設計次第で、セキュリティ・コスト・体験のバランスが大きく変わるため、実装着手前に方式（都度入力型／保存型）を確定させる必要がある。
- 料金プラン（Render/Railway等）は本日時点で一部を確認したが、**Streamlit/Gradio自体の商用利用規約・Anthropic APIの商用利用条件は自分（メイ）の専門外であり未確認**。特にAnthropic APIの利用規約適合性は[要リョウ確認]とし、本設計書はその前提での技術検討に留める。
- 「顧客が自分のAPIキーを入力する」構成は、①サーバー側の平文保持を避ける設計、②パスワード共有・不正利用によるサーバー側コスト増（顧客のAPI利用料ではなく、こちら側のRender/Railway等のホスティング費用）の2点が主要リスク。これらは設計段階で対処可能。
- アプローチ②（PyArmor/PyInstaller難読化）は「顧客ローカル実行」を前提とするため、コードの逆コンパイル・メモリダンプによる復元リスクが実在し、①より流出防止性は低いと判断する（出典あり、下記参照）。運用負荷（更新のたび再配布）も①より高い。
- 実装フェーズでは、フロント/バックエンドのWeb実装をノヴァへ、n8n連携が必要になった場合（例：note購入通知→パスワード自動発行等の自動化）はエイトへ委任することを推奨する。ただし自動送信・Credential本番登録は`approval-policy.md`により社長の承認が必須。

  - 出典：https://gbhackers.com/pyarmor-obfuscation/、https://github.com/orgs/pyinstaller/discussions/9330（取得日：2026-08-01）
  - ※これらはセキュリティ解説記事であり、Anthropic公式・PyArmor公式ドキュメントそのものではない点に留意（[学説・実務見解]相当の情報源）。

  - 出典：https://support.claude.com/en/articles/9767949-api-key-best-practices-keeping-your-keys-safe-and-secure（検索結果からの要約。ページ本文を直接WebFetchでは未確認のため、内容は[要追加調査]として一次確認を推奨）

## 推測・仮説

以下は一次情報での裏付けが取れていない、業務自動化アーキテクトとしての技術的な仮説・設計判断です。

- **[仮説] Streamlit/GradioはVercelのサーバーレス実行モデルとの相性が悪い可能性が高い**：StreamlitはWebSocketによる常時接続・サーバー側セッション状態保持を前提とするフレームワークであり、Vercelが主に想定するサーバーレス関数（短時間実行・ステートレス）とは実行モデルが異なる。Render/Railway/Heroku系の「常時起動コンテナ」型サービスの方が親和性が高いと推測する。ただし本日時点でVercel公式ドキュメントでのStreamlit対応可否は直接確認していないため、[未確認]として次アクションに送る。
- **[仮説] 「都度APIキー入力・非永続化」方式が最もリスクが低い**：顧客が毎回ブラウザ上でAPIキーを入力し、サーバー側では処理中のみメモリ上に保持してリクエスト終了後に破棄する設計であれば、平文保存の問題自体を回避できると考える（詳細は「リスク・注意点」参照）。
- **[仮説] 想定顧客数が少数（数十〜百程度）の初期フェーズでは、Render Hobby/Starter または Railway Hobby程度の最小構成で十分**という仮定を費用試算の前提に置いている（後述、要検証）。

## 分析

### A. 構成要素の整理（アプローチ①）

| 構成要素 | 選択肢・設計方針 | 論点 |
|---|---|---|
| フロント（UI） | Streamlit または Gradio（Python単体で画面構築可能） | ノーコード的に早く作れる一方、UIカスタマイズ性は市販SaaSより低い。ブランド体験を重視する場合はノヴァによるカスタムWeb実装（React等＋バックエンドAPI）も選択肢 |
| 簡易認証 | 記事内アクセスパスワード（全顧客共有）／顧客ごと個別パスワード | 共有パスワードは実装が単純だが漏えい時の被害範囲が全顧客に及ぶ。個別発行は被害範囲を限定できるが発行・失効の運用（手動 or n8n自動化）が必要 |
| APIキーの扱い | ①都度入力・非保存（推奨） ②暗号化して顧客アカウントに紐付け保存 | 詳細は次項「B. APIキーの技術的注意点」参照 |
| セッション管理 | Streamlit `session_state` / Gradio `State`、またはトークンベースの独自セッション + 有効期限 | サーバー再起動でセッションが失われる設計上の制約に留意（Streamlit/Gradioの標準的な単一プロセス運用の場合） |
| ホスティング | Render / Railway（常時起動コンテナ型）を軸に検討。Vercelはサーバーレスのため上記の通り[未確認・要検証] | 同時アクセス増加時のスケーリング設計（後述） |

### B. APIキーの技術的注意点（設計原則・禁止事項に基づく）

自分（メイ）の禁止事項「認証情報・トークン類をファイルや報告に平文で残さない」に従い、以下は**設計方針の提示**であり、実キーそのものはこの報告書のどこにも含めていません。

1. **サーバー側ディスク・DBへの平文保存は行わない設計を前提とする。** 保存が必要な場合は、暗号化（例：アプリケーション層での対称鍵暗号化＋鍵管理サービス分離）を必須要件とする。
2. **最もリスクが低いのは「都度入力・非永続化」方式**：顧客が画面を開くたびにAPIキーを入力し、サーバー側ではそのセッション処理中のみメモリ上で保持、処理完了後・セッション終了後に破棄する。ディスクへの書き込み・ログ出力を行わない実装が前提となる。
3. **ログ・エラーレポートへのキー混入防止**：例外発生時のスタックトレース、アクセスログ、監視ツール（あれば）にAPIキー文字列が出力されないよう、マスキング処理を実装要件に含める必要がある。
4. **通信経路はHTTPS必須**（Render/Railway/Vercel等の主要PaaSは標準でTLS終端を提供するのが一般的だが、各社の設定要否は実装時にノヴァ／エイトが公式ドキュメントで確認すること）。
5. **顧客側の誤用対策**：顧客が自分のAPIキーを他人と共有してしまう、退職者・解約者のキーが残り続けるといった顧客側運用リスクは、こちら側の設計だけでは防げない。マニュアル（設計書内で言及されている「APIキー取得図解マニュアル」）に、キーの管理責任は顧客側にある旨を明記することを推奨する。
6. この論点は「認証情報を扱う設計」であるため、実装段階でも本人確認情報・キー自体をコード外の環境変数／シークレット管理の外部サービスに置く方針を維持し、Gitリポジトリ・チャット・報告書に一切残さないことを徹底する。

### C. 同時アクセス時のコスト・キャパシティ論点

- 設計書自身が指摘する通り、顧客が自分のAPIキーを使う構成では「AI利用料（Anthropic API負担）」は販売側に発生しない。一方で、**Webツールをホスティングするサーバー側の計算資源コスト（Render/Railway等の従量課金分）は販売側が負担する**点は区別が必要。
- Railway等は秒単位・GB単位の従量課金であることを確認済み（上記出典）。同時アクセス数が増えると、この従量課金部分（CPU・メモリ・エグレス）が増加する。
- 「顧客が自分のAPIキーを使う＝販売側のAPIコストはゼロ」ではあるが、「サーバーホスティング費用はゼロにならない」ことをコスト試算・料金設計の前提として明記する必要がある。
- パスワード共有による想定外の同時アクセス増（購入者以外の利用）は、ホスティング費用の増加に直結するリスクとして次項で扱う。

### D. アプローチ①とアプローチ②の比較（設計書内容＋今回確認した事実の統合）

| 観点 | ①Webツール化 | ②難読化・バイナリ化（PyArmor/PyInstaller） |
|---|---|---|
| 流出防止性 | コードが顧客環境に渡らないため高い | 難読化は「解析を困難にする」対策であり、確認できた情報源によれば完全な防止ではない（メモリダンプ・リバースエンジニアリングで復元され得るとの指摘あり、上記出典） |
| 顧客体験 | ブラウザのみで利用可能、環境構築不要 | ダウンロード・解凍・実行が必要。OS別対応（Windows/Mac）の検証も必要になり得る |
| 更新配布の手間 | サーバー側修正が即時全顧客へ反映される | 更新のたび顧客への再配布が必要（旧バージョンが手元に残り続けるリスクもある） |
| 運用負荷（販売側） | サーバー運用・監視・セキュリティ設計が継続的に必要 | 配布後の運用負荷は相対的に軽いが、難読化ツールの維持・OS互換性対応が必要 |
| 初期実装コスト | UI構築＋認証＋APIキー設計＋ホスティング設定 | Pythonアプリ本体＋難読化パイプライン＋実行ファイル化＋署名等（Windows/Macでの警告回避には別途コード署名が必要になる場合がある。[要追加調査]） |

**総合評価**：設計書が①を「推奨」としている判断は、今回確認できた技術情報（PyArmor/PyInstallerの防御限界に関する複数の第三者解説）とも整合的であり、メイとしても①を軸とした検討を支持する。ただし「①なら流出リスクが完全にゼロになる」わけではなく（画面操作の録画・出力結果の転載等、UIレベルでの情報流用は別問題として残る）、この点は成果物の性質上ゼロにはできない残存リスクとして認識しておく必要がある。

## リスク・注意点

1. **顧客側の環境要因によるトラブル**：顧客のブラウザ種類・バージョン、ネットワーク環境（社内プロキシ・ファイアウォール等）によりWebツールが正常動作しないケースが想定される。サポート対応範囲（どこまで販売側が対応するか）を利用規約・マニュアルに明記しておくことを推奨する。これは一般的な業務自動化アーキテクトとしての運用上の注意点であり、個別の技術トラブルシューティング手順はノヴァ／エイトの実装検証段階で具体化する。
2. **Anthropic APIの利用規約・商用利用条件は自分の専門外**：「顧客が自分のAPIキーで、販売側が用意したツール経由でAPIを呼び出す」という構成が、Anthropicの利用規約上どのように扱われるか（第三者ツール経由の利用条件、レート制限、商用転売的行為への該当性等）は法務論点であり、[要リョウ確認]とする。本設計書はこの適合性を前提とせず、あくまで技術構成の検討に留める。
3. **パスワード共有・不正利用リスク**：設計書が挙げる「返金申請アカウントのパスワード無効化」に加え、共有パスワード方式では第三者への転貸によりサーバー側コストが想定外に増加するリスクがある。顧客ごと個別パスワード発行＋利用規約での譲渡禁止明記（設計書5節に既出）が対策となる。
4. **承認ポイントの設計（`approval-policy.md`準拠）**：本構成でnote購入検知→パスワード自動発行等の自動化（n8n連携）を将来的に組む場合、「n8n等の自動化ワークフローの本番接続・Credential登録・有効化」は社長の承認が必須。メイの禁止事項「承認ポイントを設けずに外部通知・自動送信を設計しない」に従い、パスワード発行・顧客への通知メール送信等は、承認フローを経た上での実装を前提とする。
5. **料金プラン情報の陳腐化リスク**：本書に記載したRailway/Render等の料金は2026-08-01時点の検索結果・一部公式ページ確認に基づくものであり、変動する可能性がある。実装直前に公式サイトで再確認することを推奨する（Railwayは公式ページで確認済み、Renderは公式ページの直接確認ができなかったため特に再確認が必要）。

## 推奨案

1. **技術構成**：Streamlit（またはGradio）をベースに、Render または Railway（常時起動コンテナ型）にデプロイする方向で詳細設計に進む。Vercelは実行モデルの相性を[要検証]としているため、現時点では軸に据えない。
2. **APIキーの扱い**：「都度入力・非永続化」方式を初期設計の前提とする（保存型は後日、暗号化・鍵管理の設計が固まった段階で検討）。
3. **認証**：顧客ごと個別パスワード発行を目指す（初期は手動発行でも可、将来的にn8nでの自動発行を検討）。
4. **次工程の委任先**：
   - フロント/バックエンドのWeb実装・認証機構・APIキー受け渡しのセキュア実装 → **ノヴァ**
   - note購入検知〜パスワード発行・通知の自動化（必要な場合のみ、承認フロー込みで設計） → **エイト**
   - Anthropic APIの商用利用規約適合性、note特定商取引法表示・返金規約との整合性 → **リョウ**
5. 実装着手前に、Render公式サイトでの最新プラン・Streamlit商用利用条件の一次確認をメイまたはリサに依頼することを推奨する。

## 代替案

- **代替案A**：完全カスタムWebアプリ（Streamlit/Gradionoではなく、ノヴァによるフロント実装＋軽量バックエンドAPI）。UI/UXの自由度は上がるが、実装工数は増える。
- **代替案B**：アプローチ①とアプローチ②のハイブリッド（低リスク・低単価の機能はWebツール、高付加価値機能は難読化配布）。設計・サポートの複雑性が増すため、初期フェーズでは非推奨。
- **代替案C**：初期はStreamlit Community Cloud（無料枠、検索結果ベースでは私的アプリ1つまで等の制限ありと見られるが[未確認・要一次確認]）でMVPを検証し、顧客数が増えた段階でRender/Railway等の有料インフラへ移行する段階的アプローチ。
