## 結論

## 確認済み事実

- 接続先n8n環境（`https://kohomadha-n8n.top`）に対し、読み取り専用API（`GET /api/v1/workflows`、`GET /api/v1/workflows/<id>`）で実際の本番ワークフロー2件（「Googleカレンダー→Notion同期」「CRM週次品質監査（情報管理シート⇔Notion）」）をエクスポート・参照した（本セッションで実施、書き込み系APIは一切呼び出していない）。
- 既存本番ワークフローは、Notion・Anthropic(Claude)いずれの連携も専用ノードではなく `n8n-nodes-base.httpRequest`（typeVersion 4.2）＋`authentication: predefinedCredentialType`＋`nodeCredentialType`（`notionApi`/`anthropicApi`）という実装パターンで統一されていることを実例で確認した。この3ドラフトでも同パターンを踏襲した。
- 上記実例から、以下のノードtype/typeVersionが本インスタンスでの実使用実績として確認できた：`n8n-nodes-base.scheduleTrigger`(1.2)、`n8n-nodes-base.httpRequest`(4.2)、`n8n-nodes-base.if`(2.2)、`n8n-nodes-base.set`(3.4)、`n8n-nodes-base.code`(2)、`n8n-nodes-base.stickyNote`(1)。3ドラフトはこれらの確認済みバージョンをそのまま使用した。
- Anthropic Messages APIのリクエスト形式（`model`/`max_tokens`/`system`/`messages`、`anthropic-version`ヘッダーの手動付与）およびレスポンス形式（`content`配列中の`type: 'text'`ブロック）は、本番ワークフロー「CRM週次品質監査」の`Claude - Write Report`ノードの実装から確認した。
- Notion Block Children API（`GET`/`PATCH` `/v1/blocks/{block_id}/children`）のエンドポイント・メソッド・主要フィールド（`children`配列・`rich_text`構造・1リクエスト最大100ブロック・ページネーション用`next_cursor`/`has_more`）は、Notion公式APIリファレンス（https://developers.notion.com/reference/get-block-children 、https://developers.notion.com/reference/patch-block-children ）をWebFetchで確認した（2026-08-09）。
- n8n Error Triggerノードの正式なtype文字列（`n8n-nodes-base.errorTrigger`）と用途（対象ワークフローのSettings > Error Workflowで指定し、失敗時に自動起動する）は、n8n公式ドキュメント（https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger/ ）で確認したが、typeVersionと出力データの正確なフィールド構造はページから取得できなかった。
- Execute Workflow / Execute Workflow Triggerの正式なtype文字列・typeVersion・詳細パラメータ構造は、公式ドキュメント（https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executeworkflow/ 、.../n8n-nodes-base.executeworkflowtrigger/ ）からは十分に取得できなかった（ページタイトルからtype文字列を類推したのみ）。
- このn8nインスタンスの既存Credential 6件（`googleDriveOAuth2Api`／`googleSheetsOAuth2Api`／`anthropicApi`／`googleCalendarOAuth2Api`／`notionApi`／`httpBearerAuth`）にメール送信系（Gmail等）のCredentialは含まれていない（T105監査結果、`logs/common_2026-08-09_n8n実環境監査_v1.md`）。このため共通エラーハンドラー（AUTO-COM-002）の通知手段はNotionページ作成に限定した。

## 現在の仮定

- Execute Workflow / Execute Workflow Trigger / Error Triggerのtype文字列は、本インスタンスで実際に確認済みの他ノード（`scheduleTrigger`, `manualTrigger`等）の命名規則（`n8n-nodes-base.<camelCase>`）と、公式ドキュメントのURLスラッグ（小文字）を組み合わせて類推した値であり、本インスタンスでの実例確認はできていない。
- `continueOnFail: true`を設定したHTTP Requestノードが失敗した場合、後続ノードで`$json.error`に情報が格納されるという挙動は、一般的なn8nの仕様として認識しているが、本インスタンスでの実例は確認していない。
- n8nのCodeノードのサンドボックスで、`require('crypto')`等のNode標準モジュールが利用可能かは未確認のため、AUTO-CNT-001の差分判定は素朴な文字列正規化比較のみで実装し、ハッシュ関数を使わない設計にした。

## 分析（設計判断の要点）

### 1. 共通Claude API呼び出しサブワークフロー（AUTO-COM-001）

Execute Workflow Trigger → 入力検証・デフォルト適用（Codeノード、`userPrompt`必須・共通ガードレール文の付与）→ リクエストボディ生成 → Claude API呼び出し（HTTP Request、`continueOnFail`+簡易リトライ3回）→ IF成功判定 → 成功時はレスポンス整形して終端、失敗時はthrowしてワークフロー実行自体を失敗させる設計とした。失敗を握りつぶさずthrowすることで、呼び出し元・本ワークフローにError Workflow設定（AUTO-COM-002を想定）を割り当てれば自動的に通知される流れを意図している。

### 2. 共通エラーハンドラー（AUTO-COM-002）

Error Trigger → エラー情報整形（`getWorkflowStaticData('global')`による重複起動の抑止付き）→ 重複チェック分岐 → Notion通知ページ作成、という構成。**通知先のNotion database_idは未確定のため、Setノードにプレースホルダーとして持たせ、以降のノードはその値を参照するだけの構成にすることで、確定後の修正箇所を1箇所に集約した。** 現状Gmail等のCredentialが無いため、通知はNotionページ作成（受動的な記録）に限定される点を設計上の既知リスクとして明記した。

### 3. note運用マニュアル（社内版・AUTO-CNT-001）

Schedule Trigger（月次、提案値）→ 設定値検証（プレースホルダーのままの実行を防止する安全装置）→ Notion情報源・前回版の取得（並行）→ Claude用プロンプト生成 → AUTO-COM-001をExecute Workflowで呼び出し → 成否判定 → 差分判定（正規化文字列比較でノイズ防止）→ 変更ありならNotion保存先ページへ追記、変更なしならスキップ、という構成。Notion APIに子ブロック一括置換のAPIが無いため、**全置換ではなく追記方式**を採用し、ページが徐々に長くなるトレードオフを許容した（詳細は`docs/cases/AUTO-CNT-001/workflow-design.md`の案比較を参照）。免責文言は付与せず、「最終更新日時」「生成元（AUTO-CNT-001・AUTO-COM-001経由・Claude Sonnet 5使用）」のメタ情報のみを本文冒頭に追記する。

## リスク・注意点

- **本番投入前に確定が必要な`[要確認/社長]`項目が複数残っている**（次節参照）。特にAUTO-CNT-001は情報源・保存先のNotion IDが未確定なままでは一切動作しない（意図的な安全装置により、プレースホルダーのまま実行するとthrowして停止する）。
- Execute Workflow系・Error Triggerのノード仕様が本インスタンスで未確認のため、実際にn8nへインポートした際にtype/typeVersion不一致でエラーになる可能性がある。本番移行前に`n8n-schema-researcher`視点での追加確認、または実際にn8nエディタUIで各ノードを1つ作成し実際のJSON書き出しを確認する作業が必要。
- 共通エラーハンドラー（AUTO-COM-002）の通知手段がNotionページ作成のみであり、プッシュ型の即時通知ができない。重要度の高いワークフロー（例：将来のニュースダイジェスト・月次レポート）の障害検知には力不足の可能性があり、Gmail等のCredential新規作成（要承認）を含めた強化を今後検討すべき。
- AUTO-CNT-001は「情報源ページを人が随時更新しておく」という運用が前提になっており、n8nがローカルの`.claude/rules/content-draft-automation.md`等のファイルを直接読めない制約への対処である。この橋渡し用Notionページの運用（誰が・いつ・何を書くか）自体は本ドラフトの範囲外であり、社長側での運用ルール整備が必要。
- ページネーション未対応（Notion取得は`page_size=100`固定、追記は100ブロックで切り詰め）。情報源・生成結果が大きくなった場合に取得漏れ・切り詰めが発生する既知の制約。
- 静的検証・Codeロジックの机上レビューのみ実施しており、実際にn8nへインポートしての動作確認は一切行っていない（`[実行環境なしのため未テスト]`）。

## 推奨案

1. 本番登録前に、`n8n-schema-researcher`視点でExecute Workflow / Execute Workflow Trigger / Error Triggerの正確なtype・typeVersionを、n8nエディタUI上で実際にノードを1つ配置してエクスポートする方法で確認する（API経由では取得できなかったため、UI操作が必要）。
2. 社長に対し、下記「未確認事項」のうち特に(a)エラーログ格納先、(b) note運用マニュアルの情報源・保存先Notionページ、(c) トリガー頻度（月次案への同意可否）の3点を優先的に確認する。
3. 上記が揃い次第、`n8n-review`（静的検証・監査）フェーズに進み、`n8n-quality-auditor`視点での独立監査を経てから`workflows/validated/`へ格上げする。
4. AUTO-COM-001・AUTO-COM-002を先にステージング環境（あれば）または本番の非アクティブ状態で動作確認し、問題が無いことを確認してからAUTO-CNT-001の実地テストに進む（依存関係上、共通基盤の健全性が前提となるため）。

## 代替案

- Anthropic専用ノード・Notion専用ノードへの切り替え：このインスタンスでの利用可否が未確認のため今回は不採用としたが、`n8n-schema-researcher`が別途ノード一覧を確認できた場合、将来的に切り替える余地はある（既存本番ワークフロー全体との一貫性は失われる）。
- エラーログの格納先をGoogle Sheetsにする代替案：既存Credentialのみで完結する点はNotion案と同等だが、他のコンテンツ系ワークフローとの実装パターンの一貫性という観点でNotion案を優先推奨とした。
- note運用マニュアルの更新方式を全置換にする代替案：Notion API制約上、削除+再作成の複数ステップが必要になり、途中失敗時のデータ損失リスクがあるため、今回は追記方式を推奨とした。
