# 会計ツールコンバータ（弥生会計／マネーフォワードクラウド会計 → freee会計 移行自動化）技術的実現可能性検討

- 作成：メイ（AI Automation & Operations Architect）
- 関連タスク：T13「会計ツールのコンバータ構築（コホマダ金融）」
- 対象事業：コホマダ（AI・DX事業）
- 想定利用者：会計士・税理士事務所（社長の顧客層。KINOTO・個人FP事業の情報は含まない）
- 基準日：2026-09-14
- 前提：本検討はWebSearch/WebFetchで確認できる公知情報（freee developers公式サイト・freeeヘルプセンター・各社公式ヘルプの検索結果スニペット）に基づく。並行してリサが一次情報ベースで詳細調査中であり、本資料の[未確認]項目は必ずリサの調査結果と突き合わせること。

## 要約

- 弥生会計・マネーフォワードクラウド会計からfreee会計への仕訳移行は、**freee自身が「他社会計ソフトからの仕訳データ移行」機能を公式に用意しており**、CSVテンプレート（仕訳インポート用）を介した移行がすでに公式ルートとして存在する。今回作りたい「コンバータ」は、このfreee公式インポート機能への**入力データを自動整形する前段部分**と位置づけるのが最も現実的。
- 技術選択肢としては、(a) CSV/Excel変換ツール、(b) freee API直接投入、(c) ハイブリッド、の3つがあるが、**MVPは(a)のCSV/Excel変換＋freee公式インポート機能の組み合わせを推奨**する。API直接投入(b)は認可・レート制限・誤登録時のロールバック設計など難度とリスクが高く、(a)で精度を実証してから段階的に検討すべき。
- 最大の技術的難所は「変換」そのものより、**勘定科目・税区分の対応表（マッピング辞書）を事務所ごと・クライアントごとにどう作り、誰が正しさを保証するか**である。ここはツールでは完全自動化できず、必ず人間（会計事務所側の有資格者）のレビュー工程を組み込む必要がある。
- 消費税区分・勘定科目の誤変換は、決算書の科目誤り・消費税申告額の誤りに直結しうる重大リスクであり、**AIツールは「下書き・一次変換」までを担い、最終判断・freeeへの反映は必ず会計事務所側の有資格者が行う**設計を前提とする（evidence-policy.mdの「法務・金融・税務は人間の最終確認を要求する」原則、およびapproval-policy.mdの精神に整合）。
- 費用対効果の定量評価（削減工数・投資対効果）は、リサが調査中の「現状の移行手間の実態」が揃ってから確定させる。本資料では技術面の実現可能性とMVP設計の考え方までを整理した。

## 結論

1. **技術的には実現可能**。ただし「完全自動化」ではなく「人間レビューを組み込んだ半自動化」が現実的なゴールである。
2. MVPアーキテクチャは **(a) CSV/Excelベースの変換ツール＋freee公式の「他社会計ソフト仕訳インポート」機能を最終投入口として使う方式**を推奨する。freee API直接投入(b)は、(a)で精度・運用が実証されたクライアント・事務所から段階的に対象拡大する「フェーズ3以降」の選択肢とする。
3. n8nでのノーコード実装は、**CSVの読み込み・ファイル出力の部分はn8nで組めるが、勘定科目・税区分のマッピングロジックはCode（Function）ノードでの実装が実質的に必須**になる（単純な列名変換を超える辞書引き・条件分岐が必要なため）。「完全ノーコード」ではなく「ローコード」と位置づけるのが正確。
4. MVPの変換対象データは、**仕訳データ（仕訳日記帳）＋勘定科目マスタ＋取引先マスタ＋消費税区分＋期首残高**に絞る。固定資産台帳・給与関連データ・部門/品目/メモタグは対象外またはフェーズ2以降とする。

## 推測・仮説

- 「業務ベースでめちゃめちゃ手間がかかる」の具体的な内訳（何にどれだけ時間がかかっているか）は、リサの一次情報調査（ヒアリング含む）を待つ必要がある。一般的に想定される手間としては、以下が典型的だと考えられる（あくまで一般論であり、対象事務所固有の実態ではない）[推測]：
  - 弥生・MFの汎用CSVエクスポートとfreeeインポートテンプレートの列構成・文字コードの不一致の手直し
  - 事務所・クライアントごとにカスタマイズされた勘定科目・補助科目のマッピング表を毎回手作業で作成
  - 消費税区分（軽減税率・インボイス対応の有無等）の手動確認
  - 期首残高の借方・貸方整合性の手動チェック
  - 複数クライアント分を1件ずつ繰り返す反復作業
- 上記が事実であれば、(a)CSV変換方式による自動化でも工数削減効果は大きい可能性が高いが、**定量的な効果（削減時間・ROI）はリサの実態調査結果が揃うまで確定できない**[推測・要追加調査]。

## 分析

### 1. 変換対象データの整理（優先度つき）

| 優先度 | データ種別 | MVP対象 | 理由 |
|---|---|---|---|
| 最優先 | 仕訳データ（仕訳日記帳） | ○ | 移行の中核。全事務所・全クライアント共通で必要 |
| 最優先 | 勘定科目マスタ | ○ | 仕訳データの前提。マッピング表の中心 |
| 最優先 | 取引先マスタ | ○ | 仕訳に付随し、freeeインポートテンプレートにも項目がある |
| 高 | 消費税区分 | ○（ただし自動判定は「候補提示＋人間確認」に限定） | インボイス制度対応後、体系差異のリスクが高い領域 |
| 高 | 期首残高 | ○ | 期首/期中乗換の判定に必須、整合性チェックが要る |
| 中 | 部門・品目・メモタグ | △（フェーズ2） | 利用有無が事務所によりばらつく。MVP後に追加 |
| 中〜低 | 固定資産台帳 | ×（フェーズ2以降） | 耐用年数・償却方法の体系差が大きく個別対応が必要 |
| 低 | 債権債務 | ×（フェーズ2以降） | 仕訳データからの派生管理になっているケースが多く、個別設計が必要 |
| 対象外（MVP） | 給与関連データ | × | 会計ソフトの範囲を超え、給与計算ソフト連携が別途絡むため、本コンバータのスコープ外とすべき[推奨] |

### 2. 技術アーキテクチャの選択肢比較

**(a) CSV/Excelベースの変換ツール**
- 概要：弥生・MFのエクスポートCSVをパースし、freeeの「他社会計ソフト仕訳インポート」テンプレート形式にマッピング変換するスクリプト/アプリ。最終投入はfreee公式のインポート画面（人間がアップロード・プレビュー確認）を使う。
- メリット：freee公式のインポート機能をそのまま「人間による最終確認ゲート」として活用できる。OAuth認可・トークン管理が不要。誤変換があってもfreee本番データに直接影響しない（インポート前にプレビューで気づける）。実装難易度が相対的に低く、n8nでも「CSV読み込みノード＋Code(マッピング)ノード＋CSV書き出しノード」で組みやすい。
- デメリット：freeeへの取り込み自体は人間が都度UIで行うため、「完全自動化」ではない（承認ゲートがある分、意図的な半自動）。データ量が多い場合はfreee側のインポート行数上限（検索結果では50,000行という情報あり、[未確認][要追加調査]）に応じた分割が必要になる可能性。

**(b) freee会計API連携による自動投入**
- 概要：OAuth2.0で認可を得て、`deals`（収入・支出）または`manual_journals`（振替伝票）APIで仕訳を自動作成。
- メリット：真の意味での完全自動化が可能。複数クライアント・複数事務所を一括処理するシステム化がしやすい。
- デメリット：事務所・クライアントごとにOAuth2認可・リフレッシュトークン管理が必要（security-policy.mdの認証情報管理原則に照らし運用負荷が高い）。レート制限（具体的数値は[未確認]だが「1分あたりの呼び出し回数上限」が存在することは確認済み）により大量データ投入時に時間がかかる。誤登録時のロールバック（削除API操作の設計）が必須で、実装難易度・保守コストが(a)より高い。n8nでは専用ノードが存在しないため、HTTP Request+OAuth2 Credentialでの実装となり、ページネーション・エラーハンドリングを自前で組む必要がある。

**(c) ハイブリッド（変換はローカル、投入のみAPI）**
- 概要：マッピング変換までは(a)と同様にローカルで行い、人間が変換結果を承認した後、投入だけをAPI経由で自動実行する。
- メリット：人間レビュー（承認ポイント）を明確に設計でき、approval-policy.mdの精神と整合しやすい。投入作業自体の手作業（freee UI上でのCSVアップロード操作）は削減できる。
- デメリット：(a)より実装難易度・コストは高いが、(b)の「全自動」よりはリスクを抑えられる。OAuth管理の負荷は(b)と同様に発生する。

**n8nでの実装可否まとめ**：(a)(c)の変換部分はn8nの標準ノード（Read/Write Binary File、Spreadsheet File、Code）で構築可能。ただし勘定科目・税区分のマッピングロジック自体は「辞書データを引いて条件分岐する」処理になるため、Codeノードでのロジック実装が事実上必須であり、purely ノーコードとは言い切れない（ローコード）。(b)(c)のAPI投入部分は、freee専用ノードが存在しない前提のためHTTP Request+OAuth2 Credentialでの実装となる。

### 3. マッピングルール設計の難所

- **勘定科目体系の対応表**：弥生・MF・freeeはそれぞれ独自の勘定科目コード体系を持ち、さらに事務所・クライアントごとにカスタム科目（補助科目・部門科目）を追加しているケースが多い。1:1で機械的に対応できない科目（統合・分割が必要なもの）が必ず発生する前提で設計する必要がある。→ 対応表は「事務所ごと・クライアントごとに保守可能なマスタデータ」（スプレッドシート等）として管理し、**初回移行時は必ず人間（会計事務所側の有資格者）のレビューを経る**設計とすべき[推奨]。
- **消費税区分の自動判定**：インボイス制度対応後、税区分・税率・軽減税率対象・適格請求書発行事業者番号の有無等、ソフト間でコード体系・粒度が異なる可能性が高い。自動判定の精度を100%保証することはできないため、「自動マッピング（候補提示）＋差分レポートでの人間確認」を必須工程とする[推奨]。
- **借方貸方合計の整合性チェック**：変換後、仕訳単位・バッチ単位で借方合計＝貸方合計になっているかを機械的に検証するバリデーション工程を必ず組み込み、不一致の仕訳はインポートせずエラーリストとして出力する。
- **エラー時のロールバック／差分レポート**：(a)方式ではfreee UI側のインポートプレビュー機能を人間チェックの最終防波堤として活用できる。(b)(c)のAPI投入方式では、投入前の検証環境（サンドボックス等）の有無は[未確認][要追加調査]であり、投入後に一括取り消しできるようバッチID・タグを仕訳メモ等に付与し、ロールバック手順をあらかじめ設計しておく必要がある。

### 4. リスクと限界

- **データ量が多い場合のAPI Rate Limit・処理時間**：1分あたりの呼び出し回数に上限が存在すること自体は確認できたが、具体的な回数は[未確認][要追加調査]。大量仕訳（例：1クライアント年間数千〜数万件）を一括投入する場合、分割・待機処理が必要になり、処理時間が相応にかかる可能性がある[推測]。
- **変換ミスの会計上の影響**：誤った勘定科目・税区分での投入は、決算書の科目残高誤り・消費税申告額の誤りに直結しうる重大リスクである。特に税区分の誤りは追徴課税等のリスクに繋がりうるため、**税務・会計上の最終確認は必ず税理士・会計士が行うものとし、本ツールはあくまで「下書き・一次変換」を担う位置づけ**とする（evidence-policy.md原則10「法務、金融、税務、補助金、許認可は人間の最終確認を要求する」に整合）。
- **完全自動化が困難な領域**：新規勘定科目の初回マッピング判断、期首残高の整合性確認、固定資産台帳（耐用年数・償却方法の体系差異）、給与関連データ（給与計算ソフトとの連携が別途絡み、単純なデータ移行では完結しない可能性が高い）、部門・品目・メモタグ等の事務所独自運用ルール。これらは人間のレビュー・判断が必須の領域として、MVPスコープ外または「候補提示＋要確認」に留める設計とする。

## リスク・注意点（まとめ）

1. 本資料の仕様面の記述（行数上限・レート制限の具体的数値等）は、egressプロキシ制限により一次情報ページを直接確認できておらず、検索結果スニペットに基づく。**着工前に必ずリサの一次情報調査結果と突き合わせて確定させること**。
2. 消費税・勘定科目の誤変換は会計・税務上のリスクに直結するため、**人間（有資格者）のレビュー工程を省略した完全自動投入は行わない**。
3. OAuth2トークン等の認証情報は、`.claude/rules/security-policy.md`に従い、成果物・報告に平文で残さない。API連携方式を採る場合、事務所ごと・クライアントごとのトークン管理設計（保管場所・アクセス権限）を別途詰める必要がある。
4. freee本番環境・クライアントの実データへの投入操作は、`.claude/rules/approval-policy.md`（金融・資金に準ずる重要データ操作）の趣旨に照らし、少なくともMVP〜フェーズ2の段階では人間の最終承認を経てから実行する運用とする。

### MVPアーキテクチャ
**(a) CSV/Excelベースの変換ツール＋freee公式インポート機能**を最終投入口とする構成を推奨する。

```
[弥生 or MF エクスポートCSV]
   ↓（読み込み・パース）
[マッピング辞書（勘定科目・税区分・取引先の対応表／事務所ごとに保守）]
   ↓（変換・借貸整合性チェック・税区分候補提示）
[freeeインポートテンプレート形式CSV ＋ 差分/エラーレポート]
   ↓（人間：会計事務所側の有資格者が確認）
[freee公式「他社会計ソフト仕訳インポート」機能でアップロード]
```

- 実装形態：Pythonスクリプト／n8nワークフロー（Code ノードでマッピングロジックを実装）のいずれでも可能。エイト（n8n実装担当）と連携し、実装方式の最終選定はn8n-automation-design Skillに沿って詰める。
- マッピング辞書は事務所・クライアントごとに保守できる形（スプレッドシート等）で管理し、初回移行時は必ず人間レビューを挟む。

### 段階的ロードマップ（案）

| フェーズ | 期間目安 | 内容 |
|---|---|---|
| フェーズ0：PoC | 1〜2週間 | 特定1事務所・特定1クライアントの実データ（弥生またはMF、直近1期分）を用い、(a)方式で「仕訳データ＋勘定科目マスタ」のみ対象に変換精度・整合性チェック機能を検証 |
| フェーズ1：MVP | 4〜6週間 | 取引先マスタ・消費税区分・期首残高を追加。マッピング辞書を事務所ごとに保守できる形に整備。差分／エラーレポートの自動生成を実装 |
| フェーズ2：横展開 | フェーズ1完了後 | 複数事務所・複数クライアントへ展開。n8nワークフロー化（アップロード→変換→検証→レポート）。部門・品目・メモタグへの対応拡大を検討 |
| フェーズ3：API投入検討（任意） | フェーズ2の実績を見て判断 | フェーズ1〜2で変換精度・運用が実証できたクライアントに限り、(c)ハイブリッド方式でのAPI投入自動化を検討。OAuth管理・ロールバック設計を含め、別途技術検討を行う |

※期間は一般的なMVP開発の目安であり、確定した見積りではない[推測]。リサの調査結果（対象事務所数・データ量・現状工数）が揃った時点で、ミナ（Finance, FP & Subsidy Analyst）と連携し費用対効果分析を確定させることを推奨する。

### 承認・監査ポイント
- マッピング辞書の初回作成・変更時：会計事務所側の有資格者によるレビューを必須とする
- freeeへの実投入（(a)方式ではUIアップロード、(b)(c)方式ではAPI投入）前：差分・エラーレポートの人間確認を必須とする
- 本ツールをコホマダの正式サービスとして外部提供する場合の契約・免責事項：リョウ（法務）への確認を推奨

## 代替案

1. **freee公式の「他社会計ソフトから仕訳データを移行する」機能をそのまま使い、コンバータは作らずマッピング表テンプレート（スプレッドシート）と作業手順書の整備に留める**案。開発コストゼロで着手できるが、手作業部分（列の並べ替え・文字コード変換・科目対応の都度判断）は残る。PoCの前段、または開発予算が確保できない場合の代替として検討可能。
2. **弥生・MF側の既存のAPIやエクスポート機能の詳細（フォーマット差異）を精査せず、汎用的なCSVマッピングツール（Excelパワークエリ等の既存ツール）を活用**する案。開発不要だが、事務所側での運用習熟・保守が必要になり、複数事務所への横展開時のスケーラビリティに欠ける。
3. **freee API直接投入(b)方式を最初から採用**する案。開発初期からの完全自動化を狙えるが、認可・レート制限・ロールバック設計のリスクが高く、今回の「MVPで早期に価値検証する」方針には適さないため非推奨（フェーズ3として温存）。
