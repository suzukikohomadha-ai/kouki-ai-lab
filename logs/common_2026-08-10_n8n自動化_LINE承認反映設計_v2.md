### 新規調査：Google Drive/Docs APIでのGoogleドキュメント新規作成（本セッションでGoogle公式ドキュメント・n8n公式ドキュメントを確認、確認日2026-08-10）

- **Google Docs API `documents.create`には、作成先フォルダを指定するパラメータが存在しない**。新規ドキュメントは常にユーザーのMy Driveのルートに作成され、特定フォルダに配置するには別途Drive APIでの移動操作が必要になる（出典：Google公式コミュニティフォーラムでの複数の質問・回答、`https://developers.google.com/workspace/docs/api/how-tos/documents`〔Docs API公式ガイド〕にはフォルダ指定オプションの記載がないことも確認。ただしこの「移動が必要」という情報自体は公式ドキュメント本文からの直接引用ではなく、複数の技術コミュニティ情報を根拠としているため`[要公式確認]`とする）。
- **これに対し、Google Drive API `files.create`は、リクエストボディに`parents`フィールド（フォルダIDの配列）を指定することで、作成と同時に目的のフォルダへ配置できる**。`mimeType`を`application/vnd.google-apps.document`に指定すれば、空のGoogleドキュメントファイルを直接目的のフォルダ内に作成できる（出典：`https://developers.google.com/workspace/drive/api/guides/create-file`、2026-08-10参照）。
- **Drive API `files.create`にメディア（コンテンツ本体）を同時アップロードする場合、アップロード元の形式（例：`text/plain`や`text/html`）とターゲット形式（`mimeType`メタデータで指定するGoogle Workspace形式）が異なる場合、Driveが自動変換する**（「Import to Google Docs types」、出典：`https://developers.google.com/workspace/drive/api/guides/manage-uploads`、2026-08-10参照）。この変換はmultipart upload（メタデータ＋メディア本体を1リクエストで送信）で実現される。
- **n8n公式のGoogle Driveノードには「Create from Text」操作があり、「Convert to Google Document」オプションを有効にすると、テキスト内容をGoogleドキュメント形式に変換して作成できる**（n8n UI上の説明として「Google Docs APIをGoogle API Consoleで有効化する必要がある」旨の記載があることを確認、出典：`https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.googledrive/file-operations`、WebSearch経由での確認、2026-08-10）。パラメータにはFile Content・File Name・Parent Drive・Parent Folderが含まれ、フォルダ指定も可能であることを確認した。ただし、この「File Content」に**HTML等のリッチな構造を渡した場合に見出し・表・取り消し線等の書式がGoogleドキュメント側に反映されるか（＝Driveの変換ロジックが入力コンテンツのMIMEタイプをどう判定するか）は、n8n公式ドキュメントの記載だけでは確認できず`[要インスタンス確認]`**とする。
- 同ノードの「Upload」操作には、公式ドキュメント上「Convert to Google Document」に相当する明示的なオプションの記載を確認できなかった（WebFetch経由での確認、`[要公式確認]`。Drive API自体はUpload〔multipart〕でも変換可能なはずだが、n8nノードのUI上でどう表現されているかは別問題であるため、実装時に改めてn8n UIで確認が必要）。
- **Google Docs API `documents.batchUpdate`にテキストを挿入する`insertText`リクエストは、`location.index`（UTF-16コード単位のインデックス）と`text`（挿入文字列）を持つ**（出典：`https://developers.google.com/workspace/docs/api/how-tos/move-text`、2026-08-10参照。ただし本ページから直接得られた確認は限定的で、コード例からの推定を含むため、正確なフィールド網羅性・レスポンス形式は`[要公式確認]`のまま残す）。見出し・太字・取り消し線・表といった書式付き更新には、`insertText`以外に`updateParagraphStyle`・`updateTextStyle`・`insertTable`等の追加のリクエスト種別が必要になると考えられるが、これらの正確なJSON形式は本セッションでは確認していない（`[要公式確認]`）。
- **Google Drive APIのOAuthスコープ**：`drive.file`（アプリが作成またはユーザーが明示的に開いたファイルのみにアクセス、非機微スコープ）と`drive`（Drive内の全ファイルへの読み書き、機微スコープ）が存在する（出典：`https://developers.google.com/workspace/drive/api/guides/api-specific-auth`、2026-08-10参照）。**重要な設計上の含意**：`drive.file`スコープだけでは、既存の（このアプリが作成していない）v1.0〜v1.11のバージョンファイルを一覧・読み取りすることができない可能性が高い。トピックバンク在庫確認・最新版検索には既存ファイルの読み取りが必須であるため、`drive.file`単独では不十分であり、`drive.readonly`（既存ファイルの読み取り用）と`drive.file`（新規作成用）の組み合わせ、または`drive`スコープ単独のいずれかが必要になると考えられる（分析6節で詳述）。
- **n8nには、任意のOAuthスコープを指定できる汎用の「Google OAuth2 API」Credential種別が存在する**（`oauth-generic`、出典：`https://docs.n8n.io/integrations/builtin/credentials/google/oauth-generic`、WebSearch経由での確認、2026-08-10）。スペース区切りで複数スコープを指定でき、HTTP Requestノードから`genericCredentialType`として利用できる。これにより、Drive読み取り・Drive書き込み・Docs書き込みに必要な複数スコープを1つのCredentialにまとめて付与し、HTTP Requestノードで両APIを呼び分けることが技術的に可能と考えられる（ただし本インスタンスでの実例確認はしておらず`[要インスタンス確認]`）。

### 6. 【新規】AUTO-CNT-002 Phase 1：note運用計画書の分析・下書き生成

依頼1節（既存ルーティンのロジック再現）に対応する、v1にはなかった新しい処理群。AUTO-CNT-001とは独立した新規のSchedule Triggerを持つサブフローとして設計する（AUTO-CNT-001と同じワークフローファイル内に同居させるか、さらに別ファイルに分けるかは実装時の判断だが、責務としては明確に分離する）。

**ノード構成（設計レベル）：**

1. **Schedule Trigger（月次）**：cron案 `0 30 0 1 * *`（UTC 00:30＝JST 09:30、毎月1日）。AUTO-CNT-001（JST 09:00）から30分ずらすことで、少なくとも同一ワークフロー同士の実行順序の意図は明確にできる。ただし既存クラウドルーティン（Claude Codeのクラウド実行、時刻に幅がある）との重複防止には時刻調整だけでは不十分であり、分析8節のガードで補う。cron値自体は`[要確認/社長]`（既存ルーティンとの時間的な棲み分けについて社長の意向を確認したい）。
2. **Google Drive：最新版検索**：`parentId = 0AH8YWDlKwoFBUk9PVA`配下で、ファイル名が「コホマダ note運用計画書 v」を含むファイルを一覧取得する。実装方式は分析7節の比較を参照（HTTP Requestで`GET https://www.googleapis.com/drive/v3/files?q=...&fields=files(id,name,createdTime)`を直接呼ぶか、n8n公式Google Driveノードの検索/一覧操作を使うか）。
3. **最新バージョン番号の算出（Codeノード）**：取得したファイル名から正規表現`/v(\d+)\.(\d+)/`でメジャー・マイナー番号を抽出し、コード側で最大値を計算する（v1の分析3節7と同じ考え方。Notionの`更新日`同様、Driveの`modifiedTime`にも依存せず、ファイル名からの抽出値を正とする）。抽出できないファイルが見つかった場合は安全側に倒して処理を中断する（架空のバージョン番号を採番しない）。
4. **最新版の本文取得（Google Drive Export）**：特定した最新版のファイルIDに対し、Drive APIの`files.export`（`mimeType=text/plain`または`text/html`）を呼び出し、本文を取得する。**この工程が本設計の核心であり、AUTO-CNT-001のNotion参照だけでは得られない実データを取得するために必須**（確認済み事実節参照）。書式（見出し・表・取り消し線相当の表現）を保持したいか、プレーンテキストで十分かにより、`text/plain`と`text/html`のどちらでエクスポートするかが変わる（分析7節と連動）。
5. **Notion「📝コンテンツ下書き・DB」クエリ**：`notion-query-data-sources`相当のNotion API呼び出し（データベースクエリ、`POST /v1/databases/{database_id}/query`または新しいdata source単位のクエリエンドポイント。Notionが2025年以降、複数データソースを持つデータベースの仕様変更を行っており、本エージェント環境の`notion-query-data-sources`ツールはSQL風の抽象化レイヤーを持つが、**n8n側のNotion API直接呼び出しでどちらのエンドポイント形式（データベース単位／データソース単位）を使うべきかは未確認**、`[要公式確認]`）で、`事業=コホマダ`かつ`媒体=note`の全ページを`createdTime`降順で取得する。
6. **新規記事の抽出（Codeノード）**：手順4で取得した最新版本文中の「作成日」記載（例：「作成日：2026年8月1日」）または、より確実な方法として**Google Driveファイルメタデータの`createdTime`**（手順2で取得済み）を基準日とし、それ以降に`createdTime`を持つNotionページを新規記事として抽出する。既存ルーティンのプロンプトは「前回の計画書バージョン作成日時」を基準にしており、テキスト内の日付記載よりもDriveファイルメタデータの方が機械的に確実なため、後者を採用することを推奨する。
7. **Claude呼び出し（AUTO-COM-001経由・分析・下書き生成）**：手順4の最新版本文（情報源・事実の一次情報として明示）、手順6の新規記事一覧（タイトル・マガジン/事業種別・ステータス・作成日時）を渡し、以下をClaudeに実施させる。
   - 新規記事とトピックバンク項目の照合（一致するもの／トピックバンクにない新規テーマ／マガジン対象外のもの、を分類）
   - マガジンごとのトピックバンク残り件数の算出。いずれかが1件以下の場合、新規候補2〜3件を提案（依頼文の既存ロジック5番に対応）

   - 「今後のアクション」等のセクションで、実施済みと確認できた項目に取り消し線相当の表現を適用した更新版本文の生成（依頼文の既存ロジック5番）

### 7. 【新規】Google Docsへの書き込み方式：2案比較（依頼2節への対応）

現状のn8n環境にはGoogle Drive/Docsへの書き込み権限を持つCredentialが存在しない（確認済み事実節）ため、いずれの案でも新規Credentialの作成が前提となる。

| 観点 | 案X（推奨・プライマリ）：Drive APIでの変換アップロード（HTML→Googleドキュメント） | 案Y（フォールバック）：空ファイル作成＋Docs API batchUpdateでの逐次挿入 |
|---|---|---|
| 実装の考え方 | Claudeが生成したMarkdown相当の構造をCodeノードで簡易HTML（見出し`<h2>`、太字`<b>`、取り消し線`<s>`、表`<table>`等）に変換し、Drive APIの変換アップロード機能（n8n公式Google Driveノードの「Create from Text」＋「Convert to Google Document」、または`files.create`のmultipartアップロード）で、目的フォルダに直接Googleドキュメントとして作成する | まずDrive API `files.create`（JSON POSTのみ、`parents`指定）で空のGoogleドキュメントを目的フォルダに作成し、続けてDocs API `documents.batchUpdate`で見出し・太字・取り消し線・表を個別のリクエスト（`insertText`・`updateParagraphStyle`・`updateTextStyle`・`insertTable`等）として逐次適用する |
| 書式の再現度 | Googleの標準HTML→Docsコンバータに依存。見出し・太字・表は一般的に高精度で変換されると推測されるが、取り消し線（`<s>`/`<del>`タグ）が正しく解釈されるかは本セッションで確認できておらず`[要検証]` | 各書式要素を明示的なAPIリクエストとして指定するため、理論上は最も正確に制御できる。ただし挿入操作のたびに後続要素の`index`がずれるため、複数の書式付き要素（見出し・表・取り消し線が混在する完全な文書）を正しい順序・インデックスで構築するロジックは本質的に複雑で、実装・保守のコストが高い |
| n8n実装の複雑さ | 中：HTTP Requestノードでのmultipart/relatedリクエスト構築（メタデータ部＋メディア部の2パート、境界文字列の管理）は生のHTTP Requestノードでは煩雑なため、**n8n公式Google Driveノードの利用を強く推奨**（multipartの複雑さをノード側が吸収する）。ただし「Create from Text」のFile ContentにHTMLを渡した場合の変換挙動は`[要インスタンス確認]` | 低〜中：各APIコール自体は単純なJSON POST（本プロジェクトの既存ワークフロー〔AUTO-COM-002等〕と同じHTTP Request＋Credentialパターンをそのまま踏襲できる）。ただし複数のbatchUpdateリクエストを正しい順序・インデックスで組み立てるCodeノードのロジックが複雑になる |
| 失敗時の影響範囲 | 1回のAPI呼び出しで完結するため、途中失敗時の状態管理はシンプル（成功/失敗の二択） | 空ファイル作成は成功したがbatchUpdateが失敗した場合、**空のGoogleドキュメントだけが目的フォルダに残る**という中途半端な状態になり得る。ロールバック処理（作成した空ファイルの削除等）を別途設計する必要がある |
| 本プロジェクトの既存パターンとの整合性 | 低：既存7ワークフロー（T105監査）はすべてHTTP Request＋Credential方式で統一されており、公式ノードの使用実績がない。案Xは本プロジェクトで初めて公式アプリノード（Google Driveノード）を使うことになる | 高：既存パターン（HTTP Request＋predefinedCredentialType）をそのまま踏襲できる |
| 参考：Google Docs API有効化の要否 | n8n公式ドキュメントに「Convert to Google Documentを使うにはGoogle API ConsoleでGoogle Docs APIを有効化する必要がある」旨の記載があり、案Xでも結局Docs APIの有効化が必要（確認済み事実節） | 同様にDocs APIの有効化・スコープ付与が必要 |

**推奨：案Xをプライマリとして採用を提案しつつ、実装フェーズで`n8n-schema-researcher`が「Create from TextのFile ContentにHTMLを渡した場合、実際にGoogleドキュメント側で見出し・表・取り消し線が反映されるか」を本インスタンスで小規模な試験作成を行って確認し、期待どおりに変換されない場合は案Yへ切り替える、という段階的な検証を推奨する。** 理由：既存クラウドルーティンが実現している書式の再現度をn8n側で目指すなら、手作業でのAPIリクエスト組み立て（案Y）よりも、Googleの変換エンジンに任せる案Xの方が実装・保守コストが低いと考えられるため。ただし、案Xが期待どおりに機能しない場合に備え、**案Yを代替案として設計に残しておく**（詳細は代替案節）。

いずれの案でも、v1.12以降の本文をどこまで既存v1.0〜v1.11の構成（見出し番号・表形式）に厳密に合わせるか、それとも簡略化するかは、依頼文の既存プロンプトが「差分を反映した更新」を想定していることから、**既存の構成・見出し番号体系をできる限り維持する形での更新（全面書き直しではなく、既存本文への差分適用に近い扱い）を目指すべき**と考える。ただし、Notionの下書きページ追記方式（Block API）と異なり、Googleドキュメントは新規ファイルとして毎回作り直す運用（v1.0〜v1.11と同じ、案A新規作成方式）であるため、「差分」といっても実際には**Claudeが最新版全文を読み込んだ上で、更新後の全文を新たに生成し直す**（既存ファイルへの部分編集ではない）という設計になる。これは分析6節の手順7で述べたとおり。

### 10. 【新規】既存クラウドルーティンとの重複防止（依頼5節への対応）

AUTO-CNT-002は、既存クラウドルーティン（`trig_01H9DAoL8ryAaUmNHsKik47X`）の実行そのものを止めたり検知したりすることはできない（両者は完全に独立したシステムであり、n8n側から既存のClaude Codeクラウドルーティンの実行状態を参照する手段は現状存在しない）。したがって、重複防止は**「AUTO-CNT-002が自分自身の実行を抑制する」形でしか実現できない**という前提に立つ。

推奨するガード：分析6節の手順3（最新バージョン検索）で取得した最新ファイルの**`createdTime`が、現在の実行月（暦月）内であれば、それがAUTO-CNT-002自身が作ったものであっても既存クラウドルーティンが作ったものであっても、Phase 1の処理をそこで打ち切り、レビューページに「今月は既に新バージョンが存在するためスキップ」の旨を記録して終了する**。

| 観点 | 案1（推奨）：暦月内1バージョンまでのガード | 案2：AUTO-CNT-002自身が作成したバージョンのみを記録し、他由来のものは無視する |
|---|---|---|
| 実装コスト | 低（手順3で取得済みの`createdTime`を比較するだけ） | 中（AUTO-CNT-002が自分で作ったバージョン番号を静的データまたはNotionに記録し、既存クラウドルーティン由来かどうかを判別するロジックが必要） |
| 既存クラウドルーティン側の意図しない上書き防止 | 効果あり（既存ルーティンが今月既に更新していれば、AUTO-CNT-002は今月は手を出さない） | 効果が限定的（AUTO-CNT-002は「自分が今月作ったか」しか見ないため、既存ルーティンが今月何度更新しても検知できず、AUTO-CNT-002が別途もう1バージョン追加してしまう可能性が残る） |
| 副作用 | 既存クラウドルーティンが暦月の途中で複数回実行された場合や、逆に今月まだどちらも実行していない場合の扱いは単純な「最新ファイルの月」判定で足りるため分かりやすい。ただし、AUTO-CNT-002側で本当に大きな変更（例：収益化企画の大幅見直し等）があった場合でも、既存ルーティンが既に今月更新済みなら**今月中は反映を待たされる**という制約が生まれる | 同上のリスクに加え、実装・検証のコストが増える |

**推奨：案1。** 「月1回程度の更新で足りる」という業務要件（依頼元の既存プロンプト自体が月次前提）に照らして、案1のシンプルさが実務上十分と考えられる。ただし、この設計は「両システムが同一月に同時に動いた場合、後から実行された方が『今月は済んでいる』と判断して自ら身を引く」という消極的な調停であり、**どちらが先に実行されるかによって、その月の最終的な内容が既存クラウドルーティンの分析結果になるかAUTO-CNT-002の分析結果になるかが変わってしまう**という残存リスクがある。この点は根本解決ではなく、次に必要なアクション節で述べるとおり、並行稼働期間そのものをできるだけ短くする（n8n版の検証を優先的に進め、目処が立ち次第、既存クラウドルーティン側を停止する）ことが本質的な解決策になる。

## リスク・注意点

v1のリスク1〜8（本体反映の二重書き込み残存リスク、署名検証未検証、「常に最新の下書きのみが承認待ち」の運用上の脆さ、`Drive File ID`空欄問題〔本設計では解消、後述〕、既存ルーティンとの重複、LINE公式アカウントマネージャーの応答設定、AUTO-CNT-001側への影響、`replyToken`有効期限）は、対象が「Notionページ作成」から「Googleドキュメント作成」に変わったことに伴う影響を除き、そのまま引き継ぐ。以下は本v2で新たに追加・変更されたリスクである。

1. **【重大】Google Docsへの書式付き書き込みの実装複雑度が本プロジェクトの他ワークフローより明確に高い**：分析7節のとおり、案X（HTML変換アップロード）・案Y（batchUpdate逐次適用）のいずれも、本インスタンスでの実機検証なしには確実な結果が読めない。特に案Yを選んだ場合、複数の書式要素を含む文書を正しいインデックスで組み立てるロジックの実装・デバッグコストは、既存のNotion Block API操作（AUTO-CNT-001・AUTO-COM-002）より高くなると見込まれる。
2. **【重大】既存の`Drive File ID`空欄問題は本設計で解消されるが、代わりに「新版がGoogle Drive上にのみ存在し、Notionカタログには自動的には現れない」という新たな空白期間が生じる**：v1では新版をNotion内に作成する設計だったため、`Drive File ID`が空欄になる問題があった（v1リスク4）。本v2では逆に、Google Drive上に実ファイルとして新版を作成するため`Drive File ID`は最初から実在する値になるが、**「🗺️ルーティン業務全体マップ」に記載のある別の既存ルーティン（Googleドライブ新着→Notionナレッジ自動登録、詳細は本セッションでは確認していない）が新版をNotionにも登録してくれることを前提にした設計**になっている。この別ルーティンが実際にどのタイミング・頻度で動作するか、あるいは現在も有効なのかは本セッションで確認していないため、**新版作成後、Notion側のカタログページ（v1.0〜v1.11のようなページ）がいつ・自動的に作られるかは未確認のまま**である。この空白期間中に鈴木さんがNotionで新版を探しても見つからない可能性がある。
3. **暦月内1バージョンのガード（分析8節）が、既存クラウドルーティンの実行タイミング次第でAUTO-CNT-002の分析結果を握りつぶす可能性**：既存ルーティンが月初に実行され「今月は済み」と判定された場合、AUTO-CNT-002がその後により精緻な分析（例：Notion DB由来のより正確なペース確認）を行っていたとしても、その回のレビュー・反映は次の暦月まで持ち越される。
4. **Claudeへの「最新版全文＋新規記事一覧」の入力によるトークン量増加**：v1.11時点で既に本文がそれなりの分量（複数節・複数表）であり、既存クラウドルーティンのプロンプトと同様の分析をAUTO-COM-001経由のClaude呼び出し1回で行う場合、AUTO-CNT-001（要約ページのみを扱う、軽量な呼び出し）よりも入力トークン数が明確に増える。処理コスト・レイテンシへの影響は`[未確認]`（実測が必要）。
5. **HTML変換方式（案X）を採用した場合、Claudeが生成したMarkdown相当の構造をHTMLに変換するCodeノードの正確性に依存する**：表の列数・入れ子構造・取り消し線の対象範囲等をClaudeの出力から機械的にHTML化する際、Claudeの出力形式が実行のたびに微妙にぶれると、変換ロジックが壊れる可能性がある。プロンプト側で出力形式を厳密に固定する設計（例：JSON構造での出力指定）を推奨する。

## 推奨案

1. AUTO-CNT-001は無変更のまま維持し、AUTO-CNT-002を「Phase 1（分析・下書き生成、新規Schedule Trigger）」「入口A（LINE確認送信、v1から流用）」「入口B（LINE Webhook受信・承認判定・反映）」の3系統を持つワークフローとして設計する（分析6節）。
2. Phase 1では、Google Drive上の最新版ファイルを実際に読み取り（Notionの要約ページだけに頼らない）、Notion「📝コンテンツ下書き・DB」の新規記事とトピックバンクを照合する分析をAUTO-COM-001経由でClaudeに行わせる（分析6節手順7）。
3. Google Docsへの書き込みは、案X（HTML変換アップロード、n8n公式Google Driveノード利用）をプライマリとして実装フェーズで試験し、期待どおりの書式再現が得られない場合は案Y（空ファイル作成＋Docs API batchUpdate）へ切り替える、という段階的な検証方針を採用する（分析7節）。
4. 新規Credential（Google OAuth2 API汎用、スコープ：`drive.readonly`＋`drive.file`＋`documents`）の作成、Google Cloud ConsoleでのDocs API有効化を、実装着手前の準備事項として社長に依頼する（分析8節）。

6. 既存クラウドルーティンとの重複防止として、「暦月内1バージョンまで」の自己抑制ガードをPhase 1の冒頭に実装する（分析10節）。
7. LINE Webhook・署名検証・Cryptoノードの正確な仕様確認、n8n-schema-researcherによるインスタンス確認は、v1推奨案6と同様に実装着手前に必須とする。
8. 実装後は`n8n-review`（静的検証・独立監査）→`n8n-test`（ステージング、特にGoogle Drive/Docs書き込みの実機テストを重点的に実施）→`n8n-deploy`（社長承認必須）の順で進める。Google Docsへの書き込みは、本番の`0AH8YWDlKwoFBUk9PVA`フォルダで直接試すのではなく、**テスト専用の別フォルダで試験作成を行い、期待どおりの書式が再現されることを目視確認してから本番フォルダを対象にする**ことを強く推奨する。
9. 並行稼働期間（既存クラウドルーティンとAUTO-CNT-002が両方稼働する期間）は、根本的な重複防止策ではなく暫定的な自己抑制ガード（分析8節）に依存する設計であることを社長に明示し、**n8n版の検証が一定水準に達し次第、早期に既存クラウドルーティンを停止する判断を促す**（並行期間を長期化させない）。

## 代替案

- **Google Docsへの書き込みを案Yに統一する代替案**：案Xの書式再現がインスタンス検証で不十分だった場合の代替。実装コストは上がるが、書式の細部まで確実に制御できる。
- **Phase 1とAUTO-CNT-001を統合し、Claude呼び出しを1回にまとめる代替案**：現在の設計はAUTO-CNT-001（社内マニュアル生成）とAUTO-CNT-002 Phase 1（note運用計画書分析）でそれぞれ独立にClaudeを呼び出す構成だが、生成対象は完全に別物（社内マニュアル vs 事業計画書）であるため、統合すると単一のClaude呼び出しが担う役割が過大になり、プロンプトの複雑化・出力形式の混在リスクが増えると考えられる。現時点では不採用とし、将来的にコスト最適化が必要になった場合の検討候補として記録する。
- **重複防止を「既存クラウドルーティンのプロンプト自体を修正し、n8n側の実行有無を確認してから動く」設計にする代替案**：技術的にはより確実な調停ができる可能性があるが、既存クラウドルーティン（Claude Codeのクラウド実行）側の変更は本設計（n8n側）のスコープ外であり、変更には別セッションでの対応が必要。将来的な改善候補として記録する。
- **レビュー専用ページを新規作成せず、AUTO-CNT-001の下書きページに統合する代替案**：ページ管理は簡素化されるが、性質の異なる2種類のレビュー対象（社内マニュアルの下書き承認 と note運用計画書本体の更新承認）が同一ページ内に混在し、v1で示した「責務ごとの分離」という設計方針と矛盾するため不採用。
