## 結論

3クラスタ相当・8ワークフロー系統（①ニュースダイジェスト6段階／②月次統合レポート／③コンテンツ下書き5種）は、いずれも「n8n Schedule Trigger → データ取得・生成 → Notion等への書き込み → 人間承認」という共通骨格を持つため、引き続き**共通コンポーネント（共有Claude API呼び出しサブワークフロー・共通エラーハンドラー・共通Notion書き込みパターン）を先に1セット作り、それを各ワークフローが呼び出す構成**を推奨する（v2から変更なし）。

- **全面n8n移行への転換（v3の中心）**：既存3種（note・KINOTO SNS/LINE・LinkedIn）を含め、最終的にすべてn8nへ統一する。ただし稼働中の業務を一度に切り替えるとダウンタイム・品質後退のリスクが高いため、**「新規2種を先行構築 → パターン実証 → 既存3種を1本ずつ段階移行（構築→並行稼働→比較→切替）→ 旧クラウドルーティン停止」**という順序を推奨する（8〜10節）。全既存3種を同時に移行対象化はしない。
- **既存n8n環境の資産（T102確定・v3で反映）**：`https://kohomadha-n8n.top`が稼働中、7ワークフロー確認済み（アクティブ：MCP Test／Googleカレンダー→Notion同期。非アクティブ：Claude Code API Test／CRM日次同期(Sheets→Notion)／CRM週次品質監査／Googleドライブ新着→Notion／タスク進捗自動チェック）。今回のプロジェクトとの名称・機能重複はない。既存Credential（Notion・Googleカレンダー・Sheets等）の再利用可能性は**T105（エイトの環境監査）待ちであり、メイは断定しない**。
- ①ニュースダイジェスト6段階・②月次統合レポートのアーキテクチャ設計（ロールアップ設計・3疎結合ワークフロー＋統合ワークフロー）はv2の結論を踏襲する（2・3節）。
- ③コンテンツ下書き5種：新規2種（note運用マニュアル社内版・公開版）を最優先で着手し、n8n＋Claude API＋Notionのパターンを実証したうえで、既存3種を優先度の高いものから段階移行する（12節で優先順位を提案）。
- 人間承認ポイントは既存パターン（下書き→アオイ相当の監査→社長承認→手動公開）をすべてのワークフローに踏襲し、n8n側は**下書き作成までしか行わない**設計を維持する。既存3種の移行時も、移行後の品質（ハルシネーション防止・免責文言・事業/媒体判定ロジック）が現行水準を下回らないことを切替前の必須条件とする（9節）。
- 障害時・切替失敗時は、10節のロールバック手順（旧クラウドルーティンへの即時切り戻し）に従う。
- n8n実行環境のURL・疎通は判明したが、バージョン・搭載ノード一覧・Credential種別等のインスタンス固有情報は依然`[要インスタンス確認]`のままであり、本設計書のノード種別・typeVersion等は一切確定させていない（T105完了後にエイトが確定）。

### 9. 既存3種の並行稼働設計（v3で新設）

既存3種（note・KINOTO SNS/LINE・LinkedIn）は、稼働中の業務であるため以下の設計を必須とする。

- **並行稼働期間の定義**：n8n側ワークフローの構築・ステージング検証が完了した後、旧クラウドルーティンを停止せずに**n8n側も並行して同一スケジュールで実行**し、両者の出力（下書き内容）を比較できる状態にする。並行稼働の具体的な期間（例：2〜4週間、または生成サイクル数ベース）は`[要決定/社長]`とし、本v3では期間の絶対値を断定しない。
- **重複実行防止との両立**：1節・項目4の重複防止ロジックは「同じ下書きの二重生成を防ぐ」ためのものだが、並行稼働期間中は意図的に**両方の系統が別々の下書き（比較用）を生成する**必要があるため、格納先を分ける（例：n8n側は比較用の一時プロパティ・タグを付与する、または別ビューに集約する）等の設計が必要。既存の「📝コンテンツ下書き・DB」に両方の出力を混在させると、社長・鈴木さんが本番用下書きと比較用下書きを誤認するリスクがあるため、比較用の出力は明確に区別できるプロパティ（例：「生成元」select：クラウドルーティン／n8n比較検証）を追加することを推奨する。
- **比較・判定基準（`[要決定/社長]`、たたき台として提示）**：
  1. 出力される下書きの品質（免責文言・プロパティ・事業/媒体判定ロジックが既存クラウドルーティンと同等以上か）
  2. ハルシネーション防止13原則の遵守状況（アオイ相当の監査基準での評価）
  3. 実行の安定性（スケジュール通りに実行され、エラーなく完了するか）
  4. 運用コスト（Claude API呼び出しコストが既存と比べて著しく増加していないか）
  - 上記4点について、並行稼働期間中の複数サイクル分をアオイまたは社長が目視比較し、n8n側が現行水準を下回らないことを確認できた場合にのみ切替を判断する。
- **既存ロジックの精査が前提条件**：v2から継続する未確認事項として、既存クラウドルーティンの実際のプロンプト本文・スケジュール定義を本セッションでは確認していない。**n8n側ワークフローの構築に着手する前に、既存3種の実装詳細（プロンプトロジック・免責文言・事業/媒体判定ロジック）を精査し、n8n側に過不足なく移植することが並行稼働設計の前提条件となる**（14節・次に必要なアクション）。

### 10. ロールバック手順（v3で新設）

n8n側で問題が発生した場合に、旧クラウドルーティンへ即座に戻せるようにするための設計方針。

- **並行稼働期間中のロールバック**：この期間は旧クラウドルーティンが稼働し続けているため、n8n側で問題が起きても「n8n側の並行実行を止める」だけでよく、業務への影響はない（ロールバックというより単純な停止）。
- **切替後のロールバック**：切替後（旧クラウドルーティン停止後）にn8n側で障害・品質問題が発覚した場合に備え、以下を必須の運用ルールとする。
  1. 切替時点で旧クラウドルーティンの設定・スケジュール定義を**削除せず、無効化（一時停止）の状態で保持する**（`.claude/skills`配下の該当スケジュール定義、または`office/state.js` routinesの該当エントリを「停止中」ステータスで残す）。
  2. 切替後、最低でも`[要決定/社長]`の一定期間（たたき台として1〜2生成サイクル分を提案するが断定しない）は、旧クラウドルーティンをいつでも再開できる状態を維持する。
  3. n8n側で重大な問題（下書き内容の事実誤認・免責文言欠落・誤った事業/媒体への投稿等）が発覚した場合、n8n側ワークフローを**即座に無効化**し、旧クラウドルーティンを**再有効化**する。この切り戻し操作自体は「毎回承認が必要な操作」（Credential・有効化操作）に該当するため、緊急時であっても社長への報告・承認を経る（無断での自動フェイルオーバーは設計しない）。
  4. ロールバック後は、n8n側の問題点を修正し、再度Phase 3（静的検証）からやり直す。
- **ロールバック手順自体の保管**：各既存ルーティンの移行時に、対象ごとの具体的なロールバック手順書（旧ルーティンの再開コマンド・設定ファイルの場所を含む）を`06-drafts`相当の場所ではなく、`n8n-automation/docs/`または本ログの追補として作成することを推奨する（Phase 4詳細設計でエイトが具体化）。

### 11. 既存n8n環境資産の再利用可能性（v3で新設、断定なし）

- **既存ワークフロー7件との関係**：T102で判明した7件（MCP Test／Googleカレンダー→Notion同期／Claude Code API Test／CRM日次同期(Sheets→Notion)／CRM週次品質監査／Googleドライブ新着→Notion／タスク進捗自動チェック）は、本プロジェクトの8系統とは名称・機能が重複しないことを確認済みという前提で設計を進める。本v3ではこの重複なし確認自体の再検証は行っていない。
- **既存Credentialの再利用可能性**：Notion・Googleカレンダー・Google Sheets等のCredentialが既にn8n上に存在する可能性が高いことは判明しているが、**実際に本プロジェクトで再利用できるかどうかは、T105（エイトの環境監査、v3作成時点で`doing, progress 0`＝未完了）の結果を待つ必要がある**。メイはこの再利用可能性について、以下のいずれであるかを断定しない。
  - 技術的に再利用可能かどうか（Credentialのスコープ・権限が本プロジェクトの用途に適合するか）
  - 運用ポリシー上、再利用が適切かどうか（既存の運用系ワークフローと用途が混在することのリスク）
- **T105完了後に確認すべき事項（エイトへの申し送り）**：
  1. n8nバージョン・搭載ノード一覧（特にAnthropic/Claude公式ノードの有無）
  2. 既存Credentialの種別一覧（値そのものではなく種別のみ、T105のhintどおり）
  3. 既存Credentialが本プロジェクトの用途（Notion書き込み、Googleカレンダー参照等）に技術的に適合するか
  4. 既存Credentialを再利用する場合の権限スコープ上のリスク（既存の運用系ワークフローに影響を与えないか）

## 代替案

- 既存3種を段階移行ではなく一括で即時切替する代替案もあり得るが、稼働中業務の品質後退リスクが高く、ロールバック時の混乱も大きいため非推奨。
- 並行稼働を行わず、n8n側の静的検証・テストのみで切替可否を判断する代替案は、実装工数・所要期間を短縮できるが、実運用データでの品質比較ができないため、2026-07-28の見落とし事故のような実運用でしか顕在化しない問題を見逃すリスクが高く非推奨。
- 既存Credentialの再利用可否が未確定のまま、暫定的に新規Credentialだけで先行実装を進める代替案は、T105の結果が判明した後の設計変更（二重管理の解消）が発生しうるが、新規2種の着手を遅らせないという観点では合理性があり、12節の優先順位（新規2種先行）とも整合するため、部分的に採用可能と考える。
- クラスタAのロールアップを「デイリー要約の再集計」ではなく「毎回生ニュースを再収集」する設計にする代替案（v2から継続）は、コスト・保守性の両面で不利なため非推奨のまま維持する。

## 12. 次フェーズ（Phase 4以降）で詳細設計すべき優先順位（v3で更新）

依存関係・リスクの低さ・既存資産の再利用しやすさ・業務インパクトを踏まえた推奨着手順序：

1. **共通コンポーネント**（1節）：T105完了後すぐに着手可能。すべての後続ワークフローが依存するため最優先。
2. **クラスタCの新規2種（note運用マニュアル：社内版・公開版）**：移行を伴わずゼロから構築でき、稼働中の業務に一切影響しないためリスクが最も低い。n8n＋Claude API＋Notionのパターンを実証する最初の実例として最適。**T105の結果を待たずに設計自体は先行して進められるが、実装（Credential登録含む）はT105完了後とする。**
3. **クラスタA：デイリーニュース収集・要約ワークフロー**：T101（情報源選定）は完了済みのため着手可能。住宅産業新聞RSSの業務利用可否確認・403系3件の疎通確認を実装前に完了させる。
4. **クラスタA：週次〜年次ロールアップ**：デイリー版が最低1サイクル安定稼働した後に着手。
5. **クラスタB：(a)活動実績・(b)業界動向レポート**：(a)は`office/state.js`データ取得手段の確定と承認要否確認（社長）が前提条件。(b)はクラスタAのロールアップ出力に依存。
6. **クラスタB：(c)n8n運用状況レポート＋統合ワークフロー**：T105完了・n8n本番稼働実績が一定期間蓄積してから着手。
7. **既存3種の段階移行（優先度：影響範囲が小さいものから）**：新規系統でパターンが実証された後に着手する。移行順は以下を提案する。
   - **7-a. コホマダnote記事（最優先で移行検討）**：週1回・1系統のみのシンプルな構成で、並行稼働・比較の検証負荷が最も小さいと考えられる。
   - **7-b. 鈴木さんLinkedIn投稿**：週1回・3領域ローテーションとやや複雑だが、投稿先が1媒体のみで比較的移行しやすい。
   - **7-c. KINOTO SNS/LINE（最後に移行）**：Instagram×2アカウント＋公式LINEと媒体数が最も多く、事業/媒体判定ロジックも複雑なため、移行の検証負荷が最も高いと考えられる。3種の中では最後に着手することを推奨する。
   - この順序（note→LinkedIn→KINOTO）は構成の単純さに基づく**メイの推奨**であり、業務上の優先度（例：KINOTOの集客を優先したい等）が別にある場合は社長判断で入れ替えてよい。
