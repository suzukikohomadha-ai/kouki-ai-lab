## 結論

既存のセルフホストn8n環境にAPI接続でき、稼働中ワークフロー7本・Credential 6件の構成を読み取り専用で確認できた。
n8n本体のバージョン番号は、今回試した公開範囲のAPIからは取得できず`[要UI確認]`とする。
Notion・Claude(Anthropic)との連携は、既存ワークフローでは専用ノードではなく**HTTP Requestノード＋該当Credential**
という実装パターンで統一されており、これは今後のワークフロー実装（T100系列）の設計方針に直結する重要な事実。

## 確認済み事実

### 1. 接続・稼働確認
- `N8N_BASE_URL`・`N8N_API_KEY`は`.env`に設定済みで、シェル変数として読み込み可能（値は未転記）。
- `GET /healthz` → `200 OK` `{"status":"ok"}`。
- `GET /rest/settings`（認証なしでも応答する公開設定エンドポイント）→ `200 OK`。取得できた設定の一部：
  - `settingsMode: "public"` / `defaultLocale: "en"`
  - `userManagement.authenticationMethod: "email"` / `smtpSetup: false`
  - `sso.saml/ldap/oidc.loginEnabled: false`（すべて無効）
  - `enterprise.saml/ldap/oidc: false`（Enterprise機能はすべて無効＝コミュニティ版相当と推定できる状態）
  - `communityNodesEnabled: true`（コミュニティノードのインストールが許可されている）
  - このレスポンスには**バージョン番号フィールドが含まれていなかった**。
- `GET /api/v1/workflows` → `200 OK`。レスポンスヘッダーに`Via: 1.1 Caddy`があり、リバースプロキシ（Caddy）経由。
  n8n本体のサーババージョンを示すヘッダーは付与されていなかった。
- `GET /api/v1/docs` → `301` → `/api/v1/docs/`（Swagger UIの静的HTMLのみ取得。JS実行なしではAPI仕様の
  `info.version`等は読み取れず、n8n本体バージョンの直接的な根拠にはならなかった）。

これらは「実際にこのインスタンス上で使用され、保存されている」という事実であり、他のノードタイプが
このインスタンスで**使えない**ことの証明にはならない（後述の未確認事項を参照）。

**重要な実装パターン**：既存ワークフローには`n8n-nodes-base.notion`のような専用Notionノードや、
Anthropic/Claude専用ノード（`@n8n/n8n-nodes-langchain.anthropic`等）は1件も使われていない。
「Notion - Create Page」「Claude - Write Report」等の名前を持つノードは、実体はすべて
`n8n-nodes-base.httpRequest`（v4.2）で、`notionApi`または関連Credentialを紐付ける形で実装されている。
例：
- `Googleカレンダー→Notion同期` の `Notion - Get existing pages` / `Notion - Create Page` /
  `Notion - Update Page` → いずれも`httpRequest`＋`credentials: notionApi`
- `CRM週次品質監査` の `Claude - Write Report` → `httpRequest`（Anthropic APIをHTTP Request経由で呼び出す実装）

### 4. 既存Credential一覧（`GET /api/v1/credentials`、全6件・種別と件数のみ）

| 種別（type） | 件数 | 参考：登録名（labelのみ、値は非取得） |
|---|---|---|
| `googleDriveOAuth2Api` | 1 | Google Drive account |
| `googleSheetsOAuth2Api` | 1 | Google Sheets account |
| `anthropicApi` | 1 | Anthropic - n8n |
| `googleCalendarOAuth2Api` | 1 | Google Calendar account |
| `notionApi` | 1 | Notion - n8n |
| `httpBearerAuth` | 1 | Bearer Auth account |

`GET /api/v1/credentials`のレスポンスに含まれるフィールドは`id / name / type / createdAt / updatedAt / shared`
のみで、シークレット値は含まれていなかった（n8n Public APIの仕様通り、値は返却されない）。

`anthropicApi`というCredential Typeが存在すること自体は確認できたが、上記3節の通り実際の呼び出しは
HTTP Requestノード経由で行われており、このCredentialが「Anthropic専用ノードで使われているか」
「HTTP Requestのヘッダー等に手動で組み込む運用か」は今回の読み取り範囲では判別できなかった
（ノードJSON上は`credentials`キーの紐付けまでは見えるが、実際にどのAuthヘッダー式で使っているかは
ノードパラメータの詳細を精査すれば分かる可能性があり、今回は概観レベルの監査に留めた）。

## 現在の仮定

- `enterprise.*`がすべて`false`であることから、Enterprise版ライセンスではなくコミュニティ版（無料版）相当
  である可能性が高いと推測するが、これは`/rest/settings`の間接的な傍証であり、公式なライセンス種別の
  確認ができたわけではない。
- ドメイン`kohomadha-n8n.top`（`.env`の`N8N_BASE_URL`、および`/rest/settings`のOIDCログインURLからも
  同一ドメインが確認できた）が本番運用中の唯一のn8nインスタンスであると仮定しているが、
  他にステージング環境等が別途存在するかは確認していない。

## リスク・注意点

- 7件中5件が無効化（inactive）状態で保存されている。既存の稼働中フロー（MCP Test、
  Googleカレンダー→Notion同期）以外は、意図的にテスト・保留中なのか、過去の作業途中なのかは
  今回の読み取り専用監査だけでは判別できない（変更履歴・実行ログまでは今回取得していない）。
- 既存ワークフローがCredential・Notion/Claude連携ともに「HTTP Requestノード＋Credential手動紐付け」で
  統一されている。T100設計書が前提とする「共通サブワークフロー」方針を実装する際も、専用ノードではなく
  この既存パターンに合わせるかどうかは設計判断が必要（可用性ではなく一貫性・保守性の論点）。
- `communityNodesEnabled: true`のため、将来的にコミュニティノードを追加インストールする余地はあるが、
  それ自体が「承認が必要な操作」に該当するかは`n8n-automation/CLAUDE.md`の権限表に照らして
  別途確認・承認が必要（今回は追加インストールを行っていない）。

1. n8nエディタ画面にログインし、UIの「Settings」または左下のバージョン表示でn8n本体バージョンを確認する

2. T100系列の実装に入る前に、既存5ワークフローの無効化理由を確認し、共通サブワークフロー化の対象に

3. Notion・Claude連携は既存パターン（HTTP Request＋Credential）に合わせて実装するか、専用ノードへ

   `n8n-automation-lead`視点で意思決定する。
