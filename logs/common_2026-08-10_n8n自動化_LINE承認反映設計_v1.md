## 結論

AUTO-CNT-001（note運用マニュアル社内版）の「下書き確認→鈴木さんが本体へ手動反映」という最終ステップを、**新規ワークフロー`AUTO-CNT-002`（仮称、既存IDと重複なし）として設計する**ことを推奨する。既存のAUTO-CNT-001は「月次で下書きを生成する」という単一責務のまま変更を最小限にとどめ、LINE確認送信・LINE返信受信・本体ページ（`コホマダ note運用計画書`シリーズ、📚ナレッジDB内）への新バージョン作成という3つの新規責務は、すべてAUTO-CNT-002に切り出す。

AUTO-CNT-002は**2つの独立したトリガー入口を持つ単一ワークフロー**として設計する。

1. **入口A（Execute Workflow Trigger）**：AUTO-CNT-001が「下書きページに実質的な変更を書き込んだ」タイミングで呼び出す。下書きページの承認状態プロパティを「承認待ち」にし、LINE Broadcast Messageで確認メッセージを送る。
2. **入口B（Webhook Trigger、常時稼働）**：LINE Messaging APIのWebhookを受信する。署名検証・重複排除を行った上で、テキストが承認キーワードに一致し、かつ「承認待ち」の下書きが一意に存在する場合のみ、`コホマダ note運用計画書 v1.12`（バージョン番号は実行時に動的算出）を📚ナレッジDBへ新規作成する。それ以外のメッセージはすべて無視する（返信・書き込みを一切行わない）。

状態管理は、**Notionページプロパティ（下書きページ自体に新規プロパティを追加）を正とする方式を推奨**し、n8nワークフロー静的データ（`getWorkflowStaticData`）は「LINEのWebhook再送・重複イベント」を弾くための補助的な軽量レイヤーとしてのみ併用する（2案比較は分析4節）。誤反映防止のため、承認とみなす返信文言は「はい」「OK」のような日常会話でも出やすい語ではなく、**この用途専用の一意なキーワード（例：「反映」）を確認メッセージ内で明示的に指定し、それ以外は無視する**設計を推奨する（分析5節）。

本体ページへの書き込みは「LINE返信で明示的に承認された場合のみ・1回のみ」に限定し、Notionプロパティによる事前チェック（承認待ちでなければ何もしない）と、書き込み直後の状態更新（反映済みへの即時更新）によって、二重書き込み（`v1.13`が誤って2つできる等）を防ぐ設計とする。ただし本設計はNotion検索（読み取り専用）で実在するv1.0〜v1.11の全件・スキーマを確認した結果、既存バージョンの本文形式が「短い変更点サマリー＋Googleドキュメントへのリンク」であり、AUTO-CNT-001が生成する下書き全文（社内マニュアル形式）とは形式が異なること、また既存バージョンには例外なく`Drive File ID`（Googleドキュメントとの同期キー）が設定されていることを確認した。この2点は本設計では完全には解消できておらず、社長判断が必要な未解決事項として明記する（分析6節・リスク節）。

### LINE Messaging API Webhookの公式仕様（本セッションでLINE公式ドキュメント・公式OpenAPI定義を直接確認、確認日2026-08-10）

- Webhookの設定は、LINE Developersコンソールの対象チャネルの「Messaging API」タブで「Use webhook（Webhookの利用）」をオンにし、Webhook URLを登録する（出典：`https://developers.line.biz/en/docs/messaging-api/receiving-messages/`）。「Webhook redelivery（再送）」というオプションも同タブに存在する。
- Webhookのリクエストボディ（`CallbackRequest`）は`destination`（Bot自身のuserId）と`events`（配列）を持つ。各イベント（`Event`）は`type`・`timestamp`（ミリ秒）・`mode`（`"active"`または`"standby"`）・`webhookEventId`（ULID形式）・`deliveryContext.isRedelivery`（真偽値）を持つ（出典：LINE公式OpenAPI定義 `line/line-openapi` リポジトリ `webhook.yml`、2026-08-10参照）。
- テキストメッセージ受信時は`MessageEvent`（`replyToken`と`message`を追加で持つ）となり、`message`は`TextMessageContent`（`text`・`quoteToken`・任意の`quotedMessageId`等）。送信元は`UserSource`（`type: "user"`、`userId`）。
- LINEプラットフォームはWebhookリクエストのヘッダに`x-line-signature`（HMAC-SHA256の署名）を付与する。受信側は署名を検証してからイベントを処理すべきとされている（出典：`https://developers.line.biz/en/docs/messaging-api/receiving-messages/`、および同ドキュメント内でリンクされる署名検証専用ページ）。
- Reply Message API（`POST /v2/bot/message/reply`）は、Webhookで受け取った`replyToken`と`messages`（1〜5件）を必須パラメータとし、認証はチャネルアクセストークンによるBearer認証（出典：LINE公式OpenAPI定義`messaging-api.yml`、2026-08-10参照）。このファイル自体には`replyToken`の有効期限の具体的な数値は記載されていなかった（後述、未確認事項）。

## 分析

### 1. ワークフロー構成案：AUTO-CNT-001拡張 vs 新規AUTO-CNT-002

| 観点 | 案A：AUTO-CNT-001を拡張（LINE送信・Webhook受信・本体反映を同一ワークフローに追加） | 案B（採用・推奨）：新規`AUTO-CNT-002`として切り出す |
|---|---|---|
| 既存の監査済み資産への影響 | AUTO-CNT-001は既にアオイの監査（`logs/common_2026-08-09_n8n実装_監査_v1.md`）を経て「情報源＝保存先」問題を解消済みの構成。ここに常時稼働のWebhookトリガーや本体書き込みノードを追加すると、**再監査の対象が「月次生成ロジック」全体に広がり**、監査コストが増える | AUTO-CNT-001は無変更（末尾に1ノード追加する程度の最小変更で済む）。AUTO-CNT-002は新規ファイルとして独立して監査でき、監査範囲を「LINE確認・本体反映」に限定できる |
| トリガーの性質の違い | Schedule Trigger（月次・同期的に完結）と、Webhook Trigger（常時稼働・非同期・実行タイミングが数日後になり得る）という性質が大きく異なるトリガーが同一ワークフロー内に混在し、可読性・保守性が低下する | トリガーの性質ごとにワークフローを分離でき、`n8n-workflow-json.md`が求める「責務ごとのサブワークフロー化」の方針にも合致する |
| 本体ページへの書き込み権限の集約 | AUTO-CNT-001に「本体ページには一切書き込まない」という明確な設計方針（Sticky Note・ノード名に明記済み）があるため、同ワークフロー内に本体書き込みノードを追加すると、この既存の安全設計上の主張と矛盾する見た目になる | 「下書き生成（読み取り専用＋下書き専用ページのみ書き込み）」と「本体反映（承認後のみ・別ワークフロー）」を物理的に分離でき、AUTO-CNT-001の既存の安全設計方針をそのまま維持できる |
| 実装コスト | 低い（既存ファイルへの追記） | やや高い（新規ファイル一式：JSON・workflow-design.md・テストケース） |

**推奨：案B。** 既に監査を通過した安全設計（本体ページに書き込むノードを一切持たない）を持つAUTO-CNT-001の性質を変えないこと、トリガーの性質（同期的な月次バッチ処理 vs 非同期の常時稼働Webhook）が大きく異なることの2点から、新規ワークフローとして分離することを推奨する。AUTO-CNT-001側の変更は「下書き書き込み成功かつ実質的な変更があった場合に、AUTO-CNT-002（入口A）をExecute Workflowで呼び出す」という1ノードの追加のみとし、変更範囲を最小化する。

### 2. AUTO-CNT-002 入口A：LINE確認送信

- **呼び出され方**：AUTO-CNT-001の`Notion - 下書きページへ書き込み（本体ページには一切書き込まない）`ノードの成功後（現在の`NoOp: 完了（下書きページ更新済み・本体は未変更）`の代わり、またはその直後）に、Execute Workflowノードで呼び出す。渡すデータ：`destinationDraftPageId`・`occurredAtJst`（今回の生成時刻）。
- **処理内容**：
  1. 下書きページ（📚ナレッジDB内、`3b7040888e9781d5aebfe8ff1f46b515`）の**ページプロパティ**を更新する。新規プロパティ（分析4節で設計）に「承認待ち」「今回の生成時刻」を設定する。**既に「承認待ち」だった場合（前回の確認依頼に社長が未回答のまま次の月次実行が来た場合）も、常に最新の生成時刻で上書きする**。これにより「常に最新の下書きのみが承認待ち状態になる」という不変条件を保つ（リスク・注意点3節で詳述）。
  2. LINE Broadcast Message（AUTO-COM-002と同じ`POST https://api.line.me/v2/bot/message/broadcast`パターンを流用）で、以下のような確認メッセージを送信する。
     > 【note運用計画書】社内マニュアル下書きを更新しました。
     > 内容確認：（下書きページのNotion URL）
     > 内容に問題なければ、このLINEに「反映」とだけ返信してください。本体『コホマダ note運用計画書』の新しいバージョンページを自動作成します。
     > それ以外の返信・他の話題への返信では反映されません。
  3. Broadcast Message送信はAUTO-COM-002と同じくレスポンスに`sentMessages`を含まないため、メッセージIDを使った「引用返信」照合はできない（既知の制約、AUTO-COM-002のnotesで確認済み）。そのため承認判定は入口Bのキーワード判定に一本化する。

### 3. AUTO-CNT-002 入口B：LINE Webhook受信・承認判定・本体反映

ノード構成（設計レベル。実際の`type`/`typeVersion`確定は`n8n-schema-researcher`の役割）：

1. **Webhook Trigger**（`n8n-nodes-base.webhook`と推測、`[要インスタンス確認]`）：LINEからのPOSTを受信。HTTP Method＝POST、認証は「None」とし（LINE標準の認証方式はヘッダ署名であり、n8n組み込みの Basic/Header/JWT authとは仕組みが異なるため）、署名検証は後続ノードで独自に行う。Raw Body（生のリクエストボディ文字列）を取得できるオプションを有効にする必要がある（HMAC計算は生のJSON文字列に対して行う必要があり、n8nがパース後のJSONを再シリアライズした文字列では元のバイト列と一致しない可能性があるため。`[要インスタンス確認]`）。
2. **署名検証（Crypto ノード＋IF）**：Crypto ノードのHmacアクション（SHA256、Crypto Credential＝LINE Channel Secretを新規登録）でリクエストボディのHMACを計算し、`x-line-signature`ヘッダの値（base64）と一致するかIFノードで判定。不一致の場合は即座に処理を打ち切る（なりすましリクエスト対策、`security.md`の「Webhookの認証・署名検証」要件に対応）。
3. **重複排除（Codeノード）**：AUTO-COM-002の`com002-normalize`と同じパターンで、`getWorkflowStaticData('global')`に処理済み`webhookEventId`を保持し（直近200件上限）、`deliveryContext.isRedelivery === true`または既知の`webhookEventId`であれば以降の処理をスキップする。
4. **メッセージ種別・送信元フィルタ（IFノード）**：`events[].type === 'message'`かつ`message.type === 'text'`のイベントのみ処理対象とする（スタンプ・画像等は無視）。送信元`source.userId`について、現時点では比較対象の確定値を持たない（後述、未確認事項）ため、当面は全件を処理対象とする（社長より「コウキAIラボ公式LINEは自分以外登録されない」と回答済みのため、実務上のなりすましリスクは限定的だが、`userId`を比較できないこと自体は設計上の残課題として明記する）。
5. **承認キーワード判定（Codeノード）**：受信テキストを正規化（前後空白除去・全角/半角統一）した上で、**この用途専用の一意なキーワード**（分析5節で詳述、推奨：「反映」を含む、かつ他の許可パターンとは完全一致）と比較する。一致しなければ、この時点で処理を終了する（**返信もしない**。理由は分析5節）。
6. **承認待ち下書きの検索（Notion HTTPノード：データベースクエリ）**：📚ナレッジDB（またはより適切な格納先、分析4節で検討）を、新規プロパティ「承認ステータス」＝「承認待ち」でフィルタして検索する（`POST /v1/databases/{database_id}/query`、Notion公式APIドキュメントで別途エンドポイント仕様を確認する必要あり、`[要公式確認]`）。
   - 結果0件 → 何もしない（承認待ちの下書きが無いのに「反映」と送られたケース。誤操作または既に処理済みの可能性が高いため、静かに終了する。必要であれば軽微なログのみ）。
   - 結果1件 → 後続処理へ。
   - 結果2件以上 → **自動処理しない**。あいまいな状態のため、LINE Reply Message（このイベント自身の`replyToken`を使用、受信直後のためこの用途では有効期限内と考えられる）で「複数の下書きが承認待ちです。管理者にご確認ください」等を返し、書き込みは一切行わない。
7. **次バージョン番号の算出（Codeノード）**：📚ナレッジDBを`種別＝note運用計画書`かつ`事業＝コホマダ`で全件クエリし、各`Name`から正規表現`/v(\d+)\.(\d+)/`でメジャー・マイナー番号を抽出、**コード側で最大値を計算する**（Notionの`更新日`ソートには依存しない。既存ページが後から編集されると`更新日`が更新され、バージョン順と`更新日`順が一致しなくなるリスクがあるため）。抽出できないページや形式外の`Name`が見つかった場合は、安全側に倒して処理を中断しエラー通知する（架空のバージョン番号を採番しない）。
8. **本体ページ作成（Notion HTTPノード：ページ作成）**：`POST /v1/pages`、`parent: {database_id: "16fa0285-535e-42c3-8836-b8fda84b7522"}`、`properties`に`Name`＝`コホマダ note運用計画書 v1.12`（算出値）、`事業`＝`コホマダ`、`種別`＝`note運用計画書`、`カテゴリ`＝`その他`（既存3ページで確認した値をそのまま踏襲）、`Drive File ID`は**空欄のまま**（分析6節）を設定する。本文（`children`）は分析6節の方式で構築する。
9. **下書きページの状態更新（Notion HTTPノード）**：ページ作成が成功したら、直ちに下書きページの「承認ステータス」を「反映済み」に更新し、「最終反映バージョン」に今回作成したバージョン番号を記録する（冪等性の担保、リスク節参照）。
10. **完了通知（LINE Reply Message）**：受信イベントの`replyToken`を使い、「v1.12を作成しました：（NotionページURL）」を返信する。

### 4. 状態管理の2案比較（依頼6節への対応）

| 観点 | 案1（採用・推奨）：Notionページプロパティで状態管理 | 案2：n8nワークフロー静的データ（`getWorkflowStaticData`）のみで状態管理 |
|---|---|---|
| 実装方法 | 📚ナレッジDBに新規select/textプロパティを追加（例：`承認ステータス`＝select［未送信/承認待ち/反映済み］、`承認待ち開始日時`＝date、`最終反映バージョン`＝text）。下書きページ自体にこれらを設定する | AUTO-CNT-002の静的データに`{pendingDraftPageId, pendingSince, latestDraftTimestamp, status}`を保持する。AUTO-COM-002の`processedErrorKeys`パターンと同じ発想 |
| 可視性・監査性 | 鈴木さんがNotionを開けば「承認待ちかどうか」が直接見える。案件のステータス管理（`document-control.md`的な発想）と親和性が高い | n8nの実行ログ・エディタを開かないと状態が分からず、鈴木さんから見て不透明。Notion上の下書きページを見ても承認状況が分からない |
| 永続性・耐障害性 | Notion側にデータが残るため、ワークフローの再インポート・ID変更（AUTO-CNT-001の実装ログで実際に発生した「ワークフローIDの不一致」のような事故）が起きても状態が失われない | ワークフローが削除・再作成されると静的データが失われる可能性がある（n8nの一般的な仕様として、静的データはワークフローレコードに紐づく）。復旧時に「承認待ちだったことを忘れる」リスクがある |
| スキーマ変更の要否 | 📚ナレッジDBへのプロパティ追加が必要（既存の他ページには影響しないが、DBスキーマ変更には該当する） | 不要。ただし「見えない状態」を増やすことになる |
| 複数下書き同時承認待ちへの対応 | Notionのデータベースクエリで複数件検出でき、あいまいな場合の分岐（3節ステップ6）が自然に実装できる | 静的データはワークフロー単位のプレーンなJSONであり、同種の検索・フィルタは自前のロジックで持つ必要があり実装が煩雑になる |
| 推奨併用範囲 | 主たる状態（正）として採用 | LINE Webhookの重複イベント（`webhookEventId`）排除にのみ限定して併用する（案2単独ではなく、案1と組み合わせる） |

**推奨：案1を正とし、案2はLINE Webhookの重複排除という狭い用途にのみ補助的に使う。** 理由は、この設計自体が依頼4節（誤反映防止）・5節（既存の安全設計との整合性）で要求している「可視性」「監査可能性」を満たすには、鈴木さん自身が確認できる場所に状態を残す必要があるため。n8nの静的データだけに状態を置くと、AUTO-CNT-001の実装過程で実際に起きた「ワークフローIDの不一致」のような事故が起きた際に、承認待ち状態そのものが消失し得る。

### 5. 誤反映防止：承認キーワードの設計（依頼3節への対応）

- 「はい」「OK」等の一般的な肯定語は、社長が全く別の用件（プライベートの会話、他の確認依頼への返信等）でLINEに送る可能性が、この用途専用のチャネルであっても否定できない。特に本設計は**返信が数時間〜数日後になる非同期の運用**であるため、確認メッセージを送った文脈を社長が覚えていない状態で「OK」とだけ返信するリスクは、即時確認型のUIより高いと考える。
- そのため、**この用途にしか使わない一意なキーワード**（例：「反映」）を確認メッセージ本文で明示的に指定し、**完全一致（正規化後）でのみ承認とみなす**設計を推奨する。「はい」「OK」等の汎用語は許可パターンに含めない。
- 承認キーワードに一致しない返信は、**一切の書き込み・返信を行わない**（依頼3節の「それ以外は無視する」に対応）。ただし「無反応」自体が社長にとって「ちゃんと届いているのか分からない」という不便を生む可能性があるため、代替案（LINE Reply Messageで軽い受領確認を返す案）を代替案節に記載する。
- 将来的な拡張案として、確認メッセージ自体をBroadcastではなくPush Message（社長の`userId`宛て）に変更できれば、返信メッセージの`quotedMessageId`（本文が確認できた公式スキーマのフィールド）を使った「引用返信のみ承認とみなす」という、より確実な照合方法が使える。ただし初回はまだ`userId`を保持していないため、これは「Webhookを一度でも受信した後の運用改善」として次フェーズの検討候補とする（本設計のスコープ外）。

### 6. v1.12作成の実装：本文形式とDrive File IDの扱い（依頼4節への対応・未解決の設計論点）

Notion実データ確認の結果、既存v1.0〜v1.11は「本文＝短い変更点サマリー＋Googleドキュメントへのリンク」「実際の詳細内容はGoogleドキュメント側」という構成であり、AUTO-CNT-001が生成する下書き全文（社内マニュアル形式の長文）とは性質が異なることが判明した。この差異への対応方針を2案提示する。

| 観点 | 案X（推奨・v1として採用）：承認された下書き全文をそのままv1.12の本文にする | 案Y：短い変更点サマリーのみをv1.12の本文にする（既存シリーズの形式に厳密に合わせる） |
|---|---|---|
| 実装コスト | 低い（下書きページの最新セクションをコピーするのみ、追加のClaude呼び出し不要） | 中（サマリー生成のための追加のClaude呼び出しが必要、またはAUTO-CNT-001のプロンプト自体を「サマリーも生成する」よう変更する必要あり） |
| 「反映」という依頼の趣旨との一致 | 承認された内容がそのままNotion本体に残るため、依頼の趣旨（レビュー済み内容を本体へ反映）に直接合致する | 承認された内容の要約のみが残り、全文はNotion下書きページ側にしか残らない（下書きページは追記され続けるため、将来的に参照しづらくなる可能性） |
| 既存シリーズとの形式的一貫性 | 低い（既存はリンク＋短文、v1.12だけ長文になる） | 高い（既存の形式をそのまま踏襲） |
| Googleドキュメントとの整合 | 対応するGoogleドキュメントは作成しない（Drive File IDは空欄のまま） | 同左（本設計はGoogle Docs書き込み権限を持つCredentialの用意を前提にしていないため、いずれの案でもGoogleドキュメントの新規作成は行わない） |

**推奨：案X。** ただし以下2点は本設計では解消できない残課題であり、社長の判断を仰ぐことを推奨する。

1. **`Drive File ID`が空欄になること**：既存12ページは例外なくGoogleドキュメントと紐づいているが、v1.12はn8nがGoogle Docsへの書き込み権限（未確認・未整備）を持たないため、Googleドキュメントを新規作成しない。空欄のまま許容するか、将来的にGoogle Docs作成機能を追加するか、あるいは「🗺️ルーティン業務全体マップ」に記載されている既存の「note運用計画書 定期更新」ルーティン（Googleドキュメント側を更新する既存の仕組み）と役割分担を整理するかは、`[要確認/社長]`とする。
2. **既存ルーティンとの重複可能性**：上記の「note運用計画書 定期更新」ルーティンの実装詳細を本セッションでは確認していないため、AUTO-CNT-002が新設するNotion直接作成の経路と、この既存ルーティンが将来的に競合しないかは`[要確認/社長][要追加調査]`とする。

## リスク・注意点

1. **【重大】本体ページ作成が「LINE返信で明示的に承認された内容のみ・1回のみ」に限定される設計の限界**：分析3節9で「ページ作成成功→直ちに承認ステータスを反映済みに更新」という順序を推奨したが、この2つのAPI呼び出しの間（ミリ秒〜秒単位のごく短い時間）にもう一つの重複イベント（LINEのWebhook再送等）が到達すると、理論上は二重にページが作成され得る残存リスクがある。分析3節3の`webhookEventId`重複排除（軽量レイヤー）と組み合わせることでほぼ解消できるが、完全にゼロにはできないことを開示する。
2. **署名検証の実装可否が未検証**：Cryptoノードで`x-line-signature`を検証する設計を提案したが、（a）Webhookノードが生のリクエストボディ（バイト列そのまま）を提供できるか、（b）Cryptoノードの出力形式（base64/hex）が`x-line-signature`の形式と一致するか、はいずれも本インスタンスでの実例が無く`[要インスタンス確認]`。ここが機能しない場合、署名検証なしでの運用（IPベースの制限や、`security.md`の要件未達のまま本番投入）というリスクの高い選択を迫られる可能性がある。
3. **「常に最新の下書きのみが承認待ち」という前提の運用上の脆さ**：分析2節1で「新しい月次実行のたびに承認待ち状態・生成時刻を上書きする」設計としたが、これは「古い確認依頼に対する返信は、常に最新の下書きへの承認として扱われる」ことを意味する。社長が「先月分の内容だけ承認したかった」場合に、実際には今月分（内容が変わっている）が反映されてしまう可能性がある。確認メッセージ本文に毎回「今回の下書き内容を指す」旨を明記する運用でリスクを下げるが、完全には防げない。
4. **`Drive File ID`空欄・本文形式の不一致（分析6節）**：既存の運用パターン（Googleドキュメント同期）から外れる新しい形のバージョンページが生まれることになり、鈴木さんが将来「なぜこのバージョンだけGoogleドキュメントが無いのか」と混乱する可能性がある。
5. **既存の「note運用計画書 定期更新」ルーティンとの重複稼働リスク**：詳細未確認のまま本設計を実装すると、2つの経路（既存クラウドルーティン／新設AUTO-CNT-002）が同時にバージョンを増やしてしまう可能性がある。
6. **LINE公式アカウントマネージャー側の応答設定が未確認のまま**：「応答メッセージ」「あいさつメッセージ」等の設定次第では、社長の返信に対してLINE公式アカウント自体が意図しない自動応答を返す可能性がある（本設計のBotの返信と紛らわしくなる）。公式ドキュメントで詳細な相互作用までは確認できておらず、実機での確認が必要。
7. **AUTO-CNT-001側への影響**：AUTO-CNT-001の末尾にExecute Workflow呼び出しを追加する変更は小さいが、既に監査済みのファイルへの変更であるため、**変更範囲が小さくても`n8n-quality-auditor`による再監査が必要**（`n8n-review`スキルの通常フロー）。
8. **Reply Message使用時の`replyToken`の有効期限**：本設計は「受信直後の同一実行内でReply Messageを使う」（3節ステップ6・10）ため、公式定義に具体的な数値の記載は無いものの実務上は問題ない可能性が高いと考えるが、LINE公式ドキュメントで明確な有効期限（一般に短時間とされる）を再確認するまでは断定しない。万一失効していた場合、Reply Message呼び出しは失敗する（`continueOnFail`で握りつぶし、Push/Broadcastへのフォールバックを検討する余地がある、代替案節参照）。

## 推奨案

1. 新規ワークフロー`AUTO-CNT-002`（仮称、既存IDと重複しないことを確認済み）として設計する（分析1節）。
2. AUTO-CNT-001への変更は「下書き書き込み成功時にAUTO-CNT-002（入口A）をExecute Workflowで呼び出す」1ノードの追加のみに限定する。

4. 承認とみなす返信は、日常会話に出やすい「はい」「OK」等ではなく、この用途専用の一意なキーワード（例：「反映」）の完全一致のみとする（分析5節）。
5. v1.12の本文は、承認された下書き全文をそのまま反映する案X（分析6節）を採用しつつ、`Drive File ID`空欄・既存フォーマットとの差異について社長の明示的な了承を得てから実装に進む。
6. 実装着手前に、`n8n-schema-researcher`にWebhookノード・Cryptoノードの正確な`type`/`typeVersion`/パラメータ（特に生ボディ取得方法）をn8nエディタUI上で確認してもらう。
7. 実装着手前に、社長に以下を確認する：（a）LINE Developersコンソールでの手動設定（後述）、（b）承認キーワードの文言（「反映」で良いか）、（c）`Drive File ID`空欄の許容可否、（d）既存の「note運用計画書 定期更新」ルーティンとの役割分担。
8. 実装後は`n8n-review`（静的検証・`n8n-quality-auditor`監査）→`n8n-test`（ステージング環境での実行、特にLINE Webhookのテスト送信・署名検証・重複排除ロジック）を経てから、`n8n-deploy`（社長承認必須）に進む。

### 社長に依頼したいLINE Developersコンソール等の手動操作（実装着手後、エイトと連携して実施）

1. LINE Developersコンソール → 「コウキAIラボ」チャネル → 「Messaging API」タブ：Webhook URL欄に、エイトが実装・本番登録した後に確定するn8n本番Webhook URL（`https://kohomadha-n8n.top/webhook/...`の形式になる見込み）を登録し、「Use webhook」をオンにする。「Verify」ボタンでの疎通確認は、ワークフローを有効化した後に実施する。
2. 同チャネルの「チャネル基本設定」タブで「Channel secret」を確認する（値はチャット等に貼り付けず、n8nのCredential作成画面に直接入力する）。
3. LINE公式アカウントマネージャー（`https://manager.line.biz/`）→ 「コウキAIラボ」アカウント → 応答設定：Webhookがオンになっていることを確認し、「応答メッセージ」「あいさつメッセージ」がオンの場合はオフへの変更を検討する（断定はしないため、実際の画面を見ながら判断していただきたい）。
4. n8n上での自己ホスト環境への外部からの到達性（ファイアウォール・リバースプロキシ設定）を、エイトまたは社長がインフラ管理者として確認する。

## 代替案

- **確認メッセージへの引用返信必須化**：Push Message化して`sentMessages`のIDを取得できるようにし、「引用返信のみ承認とみなす」設計にする代替案。誤反映防止の精度は上がるが、初回はまだ`userId`未取得であるため即座には実装できず、次フェーズの改善候補として位置づける（分析5節）。
- **キーワード一致しない返信への軽い受領確認**：無反応ではなく、キーワード不一致の返信に対してもReply Messageで「（このメッセージは承認コマンドとして認識されませんでした。反映する場合は『反映』とだけ送ってください）」のような軽い案内を返す代替案。利便性は上がるが、社長が無関係な会話をLINEに送るたびにBotが反応することになり、鬱陽しさとのトレードオフがある。当面は無反応（無視）を採用し、必要であれば運用開始後に見直す。
- **状態管理を静的データのみにする案（分析4節の案2）**：実装コストは下がるが、可視性・耐障害性の観点で不採用とした。将来的にNotion側のプロパティ追加が難しい事情が生じた場合の代替として記録しておく。
- **v1.12の本文を短いサマリーのみにする案（分析6節の案Y）**：既存シリーズとの形式的一貫性を優先する場合の代替案。追加のClaude呼び出しコストと引き換えに、既存の閲覧体験（Notionはインデックス、詳細はGoogleドキュメント）に近づけられる。
