#### 2.4 新設アクション種別「翻訳」「整形・表化」：`immediate_action`

「翻訳」（#5）「整形・表化」（#8）は、既存の`next_actions`（未来に行うべきことの候補）とは性質が異なり、**その場でClaudeに実行させて結果を返す**依頼である。そのため`next_actions`を拡張するのではなく、独立したオブジェクトを新設する。

```json
"immediate_action": { "type": "object", "additionalProperties": false,
  "required": ["requested", "kind", "output_markdown", "destination", "confidence"],
  "properties": {
    "requested": { "type": "boolean",
      "description": "会話中に『翻訳して』『表にまとめて』等、その場での処理を明示的に依頼する発言があればtrue" },
    "kind": { "type": "string", "enum": ["translation", "reformat_table", "none"] },
    "output_markdown": { "type": ["string", "null"],
      "description": "翻訳結果、または整形・表化した結果（Markdown）。requestedがfalse、または外部調査を要する依頼（＝agent_task_candidateで扱うべきもの）の場合はnull" },
    "destination": { "type": "string",
      "enum": ["thread_reply", "notion_page", "sheets", "none"] },
    "confidence": { "type": "number" }
  } }
```

**入力・出力・Slackへの返し方**

- 入力：スレッド本文そのもの（既存の`<thread>`タグ内、追加の入力元は増やさない。F5の承認範囲を超えない）。
- 出力：`output_markdown`に翻訳文または表形式の整形結果を格納。
- 判定ルール：
  - 依頼が「この英文を要約して」「先方の返信を日本語で」のようにスレッド内テキストのみで完結する場合 → `kind:"translation"`。
  - 「これ表にまとめて」「数字を並べて」のようにスレッド内情報の整形で完結する場合 → `kind:"reformat_table"`。
  - 依頼が外部調査・追加情報の収集を要する場合（例：「この市場について調べて表にして」）→ `immediate_action.requested:false`とし、代わりに`next_actions`側で`kind:"agent_task_candidate"`・`task_category:"市場調査"`として扱う（仕分け結果v1 A28行の「外部調査を伴う場合はL3（社員AI割当候補）」に対応）。
- Slackへの返し方（`destination`）：**`translation`「整形・表化」とも既定は`notion_page`（Notionにページ作成して事後報告、改善提案v1 L2の定義どおり）で確定した（決定事項4、3節）。`thread_reply`はフェーズ1の既存方針〈Botはスレッドに投稿しない〉と矛盾するため採用しない**。スキーマのenumには`thread_reply`を将来の拡張余地として残すが、n8n側のルーターは常に`notion_page`（または該当なら`sheets`）へ振り分ける固定ロジックにする。

#### 決定事項2：顧客・取引先マスタ（#14）の格納先

社長より「最適なものを提案してほしい」と設計判断を委ねられ、秘書アイが実際のスプレッドシート構造をGoogle Drive経由で確認した（F12、実データは非転記）。この事実確認を踏まえた検討結果は以下のとおり。

**既存スプレッドシートの実態（F12）**：「情報管理スプレッドシート」は3シート構成で、いずれも性質が異なる。
1. 「コンサル【案件】」：**案件（プロジェクト）単位**。状態列（アプローチ中／ヒアリング中／保留中等）で活発に手入力更新されている。会社マスタとしては最も列構成が近いが、1行＝1案件であり、1社が複数案件を持てば同じ会社が複数行に分散する（純粋な会社マスタではない）。
2. 「プロジェクト【自社】」：**自社プロジェクト単位**。顧客・取引先の管理台帳ではない。
3. 「コネクション【一覧】」：**人脈・紹介者リスト**。会話中で新しく言及される取引先とは性質が異なる（人脈経由の紹介者を指すシートであり、案件の相手方そのものとは限らない）。

**検討した案**

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 新規Notion DBを新設 | 案件DBとrelationで紐付け | 重複判定・フィルタがNotion APIで扱いやすい。将来のKINOTO/FP展開時も同じパターンを使い回せる | 社長の実務動線（既存スプレッドシート中心のリード管理）から外れ、二重管理・情報分断のリスクが高い |
| B. 既存「コンサル【案件】」または「コネクション【一覧】」へ直接追記 | 既存シートの行として自動追加 | 既存資産をそのまま使える | **手入力で活発に更新されている本番データに自動書き込みを混ぜるリスクが高い**。「状態」列（案件進捗）や「コネクション」の意味論（紹介者リスト）と、会話中に新しく言及されただけの会社名検知とは一致しない。同じ行を人とAIが同時に触る事故（上書き）のリスクがある |
| **C（確定）. 同スプレッドシート内に新規タブを追加** | 「取引先マスタ【自動登録・確認待ち】」という第4のタブを新設し、AIはここにのみ追記する（既存3シートには一切触れない） | 既存資産（同一ファイル）を活かしつつ、既存3シートの手入力データに一切干渉しない。追記専用（append-only）にすれば事故のリスクを最小化できる | 新規タブの内容を、必要に応じて社長が既存3シートへ手動転記する一手間が残る（意図的に人を介す設計） |

**確定内容**：**案C**。新規タブ「取引先マスタ【自動登録・確認待ち】」を同スプレッドシート内に追加する。

**列構成（案）**：No／検知日時／会社名（原文）／会社名（正規化キー）／担当者名／電話番号／メールアドレス／会話の要約（該当箇所）／元Slackリンク／案件キー（Notion）／転記状況（`未転記`／`転記済み`／`対象外`）／備考。

**運用ルール**：
1. **追記専用（append-only）を必須ルールとする**：既存3シート（コンサル【案件】／プロジェクト【自社】／コネクション【一覧】）の行には一切触れない（読み取りもしない。書き込み専用の新規タブに閉じる）。新規タブ自体も、既存行の値を上書きしない（重複候補が見つかった場合も、既存行を書き換えるのではなく新しい行を追加し「転記状況」に注記する）。
