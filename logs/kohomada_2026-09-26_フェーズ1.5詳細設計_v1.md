#### 顧客・取引先マスタ（#14）の設計

これは案件DBのプロパティ追加ではなく、**格納先そのものの意思決定**が要る。3節「論点2」で選択肢を整理する。重複判定キーは、会社名の正規化（全角/半角統一・法人格表記〔株式会社／(株)等〕の除去・前後空白除去・大文字小文字統一）による**決定的な文字列一致**のみを自動化対象とし、表記ゆれを超えた「たぶん同じ会社」の推測による自動結合は行わない（仕分け結果v1 J10行「誤結合の方が害が大きい」の考え方を類推適用、`[推測]`）。正規化しても一致しない場合は新規登録し、人間が後から手動統合する運用にする。

### 2. Claude抽出スキーマの拡張

現行`slk-extract v1.0`（改善提案v1 3.3.2）に対する追加項目。既存の`title`/`counterparty_org`/`summary`/`status_proposal`/`next_actions`/`deadline`/`overall_confidence`/`ambiguities`/`injection_suspected`/`pii_detected`/`evidence`は変更しない（`additionalProperties:false`の制約上、追加時は`required`配列・`properties`双方を明示的に更新する必要がある）。

#### 2.1 `status_proposal`のenum拡張

```json
"status_proposal": { "type": "string",
  "enum": ["未着手", "進行中", "社内確認待ち", "先方回答待ち", "保留", "受注", "完了", "中止", "不明"] }
```

`受注`の挿入位置は「進行中」グループの一員として扱う（1節プロパティ表参照）。

#### 2.2 契約書状態・記録種別・貿易固有項目の追加

これらはNotionへの書き込み対象だが、Claudeにも該当情報を抽出させる必要があるため、スキーマに以下を追加する。

```json
"contract_status_proposal": { "type": "string",
  "enum": ["未送付", "送付済み", "受領済み", "双方受領済み", "該当なし"] },
"record_type_proposal": { "type": "string",
  "enum": ["案件", "クレーム・返品", "不明"] },
"trade_terms": { "type": "object", "additionalProperties": false,
  "required": ["item", "quantity", "price_or_amount", "payment_terms"],
  "properties": {
    "item": { "type": ["string", "null"] },
    "quantity": { "type": ["string", "null"] },
    "price_or_amount": { "type": ["string", "null"] },
    "payment_terms": { "type": ["string", "null"] }
  } }
```

`trade_terms`は貿易案件でない場合すべて`null`。会話に無い数値・条件を作らない（evidence-policy原則3）ことをsystemプロンプトで明示する。

#### 2.3 「社員AIへの割当候補」：`task_category`の追加とn8n側ルックアップ

`next_actions`配列の各要素（既存の`text`/`kind`/`owner_role`/`confidence`）に、`kind`が`agent_task_candidate`のときのみ意味を持つ`task_category`を追加する。

```json
"next_actions": { "type": "array", "items": {
  "type": "object", "additionalProperties": false,
  "required": ["text", "kind", "owner_role", "task_category", "confidence"],
  "properties": {
    "text": { "type": "string" },
    "kind": { "type": "string",
      "enum": ["internal_status_update", "agent_task_candidate", "external_action_requires_approval"] },
    "owner_role": { "type": "string", "enum": ["社長", "AIチーム", "先方", "不明"] },
    "task_category": { "type": "string",
      "enum": ["該当なし", "市場調査", "企画_事業計画", "提案書_営業資料_会議資料",
                "契約書レビュー_法務相談", "海外法規制調査",
                "システム障害対応", "与信_信用リスク調査", "海外新規顧客開拓",
                "補助金_助成金候補", "コンプライアンス確認", "その他_要人判断"] },
```

2. n8n側にカテゴリ→担当社員の固定ルックアップテーブルを置き、`task_category`を受け取って「割当候補・担当社員候補」（multi_select）の値を機械的に決定する。

| その他_要人判断 | （割当なし。社長確認へ） | — | — |

「無効」カテゴリは、n8nルーターが検知しても**割当候補の3点セット（プロパティ11〜14）は書き込まず**、AI要約・`next_actions`のテキストとしては残す（情報として消えないが、候補として前面には出さない）。フェーズ2着手時に該当カテゴリを「有効」に切り替えるだけで済むようにする（改善提案v1 P16「今作らないものを後で作り込み直さない」の考え方を踏襲）。

このルックアップテーブルをClaudeのプロンプト・スキーマではなくn8n側のコードノード／Setノードに置く理由：(a) エージェント編成が変わったとき（`.claude/agents/`の増減）にプロンプト・スキーマを変更せず済む、(b) Claudeが実在しない社員名を生成するリスクを構造的に排除できる（evidence-policy原則3）。

#### 2.4 新設アクション種別「翻訳」「整形・表化」：`immediate_action`

「翻訳」（#5）「整形・表化」（#8）は、既存の`next_actions`（未来に行うべきことの候補）とは性質が異なり、**その場でClaudeに実行させて結果を返す**依頼である。そのため`next_actions`を拡張するのではなく、独立したオブジェクトを新設する。

```json
"immediate_action": { "type": "object", "additionalProperties": false,
  "required": ["requested", "kind", "output_markdown", "destination", "confidence"],
  "properties": {
    "requested": { "type": "boolean",
      "description": "会話中に『翻訳して』『表にまとめて』等、その場での処理を明示的に依頼する発言があればtrue" },
    "kind": { "type": "string", "enum": ["translation", "reformat_table", "none"] },
    "output_markdown": { "type": ["string", "null"],
      "description": "翻訳結果、または整形・表化した結果（Markdown）。requestedがfalse、または外部調査を要する依頼（＝agent_task_candidateで扱うべきもの）の場合はnull" },
    "destination": { "type": "string",
      "enum": ["thread_reply", "notion_page", "sheets", "none"] },
    "confidence": { "type": "number" }
  } }
```

**入力・出力・Slackへの返し方**

- 入力：スレッド本文そのもの（既存の`<thread>`タグ内、追加の入力元は増やさない。F5の承認範囲を超えない）。
- 出力：`output_markdown`に翻訳文または表形式の整形結果を格納。
- 判定ルール：
  - 依頼が「この英文を要約して」「先方の返信を日本語で」のようにスレッド内テキストのみで完結する場合 → `kind:"translation"`。
  - 「これ表にまとめて」「数字を並べて」のようにスレッド内情報の整形で完結する場合 → `kind:"reformat_table"`。
  - 依頼が外部調査・追加情報の収集を要する場合（例：「この市場について調べて表にして」）→ `immediate_action.requested:false`とし、代わりに`next_actions`側で`kind:"agent_task_candidate"`・`task_category:"市場調査"`として扱う（仕分け結果v1 A28行の「外部調査を伴う場合はL3（社員AI割当候補）」に対応）。
- Slackへの返し方（`destination`）：`translation`は既定`thread_reply`（スレッドへの返信）、`reformat_table`は既定`notion_page`（Notionにページ作成して事後報告、改善提案v1 L2の定義どおり）。ただし`thread_reply`はフェーズ1の既存方針からの逸脱であるため、**3.5節の論点として社長確認を要する**。

#### 論点1：#4受注のステータス変更を「人のみが変更できる項目」に含めるか

| 案 | 内容 | 影響 |
|---|---|---|
| A. 自動遷移を許可する | `受注`を1.5-bの信頼度閾値0.85の対象に含める。「受注した」「正式にお願いされた」という発言があれば自動でステータスが`受注`になる | 記録の即時性は高いが、受注は営業管理上の重要な区切りであり、誤記録の実害（進行中案件の誤クローズ、数字の誤集計）が`完了`／`中止`に近い |
| B. 人のみに含める | `完了`／`中止`と同じ扱いにし、AIは「AI提案ステータス」への提案のみ行い、実際の`受注`への変更は社長が行う | 安全側だが、1.5-bの効果（自動記録）がこの1点で薄れる |

**両方で動く設計**：スキーマ上は`受注`をenumに含め、AI提案ステータスへの提案は常に行う（案A・B共通）。実際に「ステータス」プロパティへの自動書き込みを許可するかどうかは、n8n側の「自動遷移許可リスト」という設定値1つで切り替えられるようにする。初期値は**案B（許可リストに含めない＝人のみ）**とし、保守的側に倒す。社長が案Aを選んだ場合は、許可リストに`受注`を追加する変更だけで済む。

#### 論点2：顧客・取引先マスタ（#14）の格納先

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 既存「情報管理スプレッドシート」を拡張利用 | 既存のGoogle Sheets（コンサル案件・リード管理）に列を追加 | 既存資産の流用、新規DB管理コストなし | 列構成が未確認`[要確認]`（F10）。Sheetsでの重複判定・フィルタはNotionクエリAPIほど柔軟でない |

#### 論点4（設計中に新たに発見した点）：翻訳・整形結果のスレッド返信は、フェーズ1の「Botはスレッドに投稿しない」方針からの逸脱

2.4節の`immediate_action.destination:"thread_reply"`は、改善提案v1 3.1節「Bot自身の投稿がスレッドに混ざる」で定めた「フェーズ1ではスレッド内への投稿自体を行わない」という方針に反する。これは仕分け結果v1が「Slackへの返し方」として翻訳結果をスレッドに返すことを前提にしているために生じた設計上の緊張であり、**社長に選んでいただく必要がある**。

| 案 | 内容 | 留意点 |
|---|---|---|
| A. スレッドへの返信を許可する | 翻訳結果をスレッド内に返信として投稿する | Bot発言除外フィルタ（改善提案v1 P9）を、返信を読み取る全ワークフローに確実に適用する必要がある（自己汚染防止、AUTO-CNT-001と同型の問題） |
| B. Notion／bot-logへの提示に留める | 翻訳結果はNotionページまたはbot-logにのみ出し、スレッドには返信しない（✅等のリアクションのみ） | フェーズ1の方針を変えずに済むが、「その場で読みたい」という利便性は下がる |

本書は両案とも技術的に設計可能な形にしてある（`destination`enumに`thread_reply`と`notion_page`の両方を用意）。既定値は保守側の**案B**を推奨する。
